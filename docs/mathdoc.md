### 1.1 术语

| 术语 | 含义 |
|---|---|
| TerminusDB | 带分支与版本历史的图数据库。MathDoc 把文档节点（文字、LaTeX、Lean、Rocq 块与依赖边）存在这里 |
| 数据库 / 工作区 | 一个 TerminusDB 数据库，有一个 owner 和按分支的角色（owner、editor、viewer） |
| LeanGround | 外部证明服务：登记命题身份与定义、检查证明、保存认证、组装完整证明 |
| 认证 | LeanGround 记下的一条事实：「在这些前提下，这条命题成立」。写入后不改也不删 |
| 草图（sketch） | 带前提的认证：子引理写成证明为 `sorry` 的「前提占位」，再用它们证出目标。由组件 `lean-worker-sketch` 检查 |
| 完整证明（leaf） | 没有前提的认证，由组件 `lean-worker` 检查 |
| GoalKey | LeanGround 对「某个环境下的一条命题」算出的 64 位十六进制 SHA-256 身份。变量改名不改变它，陈述一改就是另一个目标 |
| 目标 | 一条待证的命题，身份是 GoalKey，本身没有名字 |
| 拆法 | 一条草图认证：把目标化成几个子目标 |
| AND-OR 图 | 证明图的形状：目标只要有一种拆法走通就算证出（或），一种拆法要所有子目标都证出（且） |
| 证明环境 | 基座（Lean 版本与库）、上下文（`open`、`set_option` 等）、选项、最低信任等级。环境是 GoalKey 的一部分 |
| 项目看板 | 一个数据库在一个证明环境下的协作状态：目标、认证、任务、租约、预算、各分支的路线。存在 PostgreSQL 中 |
| 挂载分支 | 把一个分支的文档从项目根节点开始转换，并提交给 LeanGround |
| 选择（pick）/ 路线 | 分支在某个目标上选用的认证；一个分支全部选择的集合就是它的路线 |
| 租约 | 领取任务后获得的限时占用权，可以续期；带 epoch（代次号），过期或被他人接手后，旧持有人不能再结束任务 |
| 组装 | 把一条路线上的认证拼成一份没有前提的源码，由 `lean-worker` 从头检查 |
| 回写 | 把组装通过的源码写回 TerminusDB 的某个分支 |
| 幂等键 | 请求附带的唯一 ID，服务端见到同一个键时返回第一次的结果，不会再执行一次 |
| `mdc` | MathDoc 的命令行，是 HTTP API 的客户端 |
| 目标草稿 | 服务端为一个目标给出的材料：结论的名字与签名、可用前提、所用定义的源码、环境上下文、任务与租约。`mdc pull` 据此写出工作文件 |
| 工作文件 | `mdc pull` 写出的 Lean 文件，格式为 `mdc-goal-file/1`：分隔行以上是只读前段，以下是可编辑正文（§4.11） |
| `.mdc/` | 工作文件旁的记录目录：每个文件对应哪个目标、租约、每次提交的幂等键与修订号。不保存令牌 |

## 2. 产品规划

### 2.1 定位与边界

MathDoc 是数学知识的协作应用。它负责提出问题、组织协作、审阅成果、展示知识：数学知识以带版本的依赖图保存，
人和 Agent 一起把其中的定理证完。

| 由 MathDoc 做 | 不由 MathDoc 做 |
|---|---|
| 文档、依赖图、LaTeX 展示、分支与历史 | 证明的对错：由 LeanGround 的验证组件裁决 |
| 目标、任务、租约、预算、拆法的启停与选择 | 证明搜索：由 Agent 自己完成 |
| 把文档节点转换为 LeanGround 请求，并把结果回写文档 | 本地 Lean：已从默认构建与部署中移除 |
| 身份与文档权限 | 与 EvoHarness 的集成（不在本轮范围） |

本文只描述 `codex/mathdoc-coordination`（主要工作分支，远端 `colab`）及由它派生的分支：TypeScript 后端，证明交给 LeanGround。
`main` 上的旧 Rust 应用不在本文范围内。

### 2.2 分工

下表回答：协作中谁负责什么。

| 参与方 | 负责 | 产出 |
|---|---|---|
| MathDoc 协调层 | 哪些目标值得做、谁来做、投入多少、用哪种拆法；文档审阅与回写 | 任务、选择、组装请求、文档修订 |
| LeanGround | 命题身份、定义登记、认证事实、推导、固定计划、组装认证 | GoalKey、定义 ID、认证 ID、计划 ID |
| 验证组件 | 裁决一份证明本身对不对：`lean-worker`（完整证明、组装）、`lean-worker-sketch`（草图） | 验证证据 |
| Agent（Codex、Claude Code、脚本） | 写证明、提拆法，通过 `mdc` 或 HTTP 接口交付 | 提交 |
| 维护者 | 冻结根陈述，审阅拆法是否值得做，组装、接受回写 | 决定 |

协调层可以记录「某个 Agent 声称完成了」，但只有读取并核对 LeanGround 的认证之后，才显示数学上的进展。

### 2.3 Project 模型：一条定理，一张共享证明图，分支是路线

**一个 Project 对应一个数据库，证明一条定理（根）**，它由三样东西固定：

- 数据库的证明环境；
- 根节点；
- owner、成员和预算。

**所有分支共享一张看板**：目标按 GoalKey 去重，认证只追加。所以一个分支证出的引理，在所有分支上同时生效，
不需要导入。

**分支不是图的拷贝，而是共享图上的一条路线**：在沿途的目标上各选一种拆法，再加上分支自己的文档。
这和 git 的结构相同：git 的对象库按内容寻址、所有分支共享，分支只是指针。对应到这里：

- LeanGround 的事实库相当于共享对象库（GoalKey 和认证 ID 都按内容寻址）；
- MathDoc 的分支相当于指针（路线加蓝图文档）。

```
Project（= 一个 TerminusDB 数据库）
│  根陈述 T（冻结）+ 证明环境（冻结）+ 成员
├─ 共享证明图（一张看板，一个 LeanGround 项目范围）
│     T ──┬── D1 ⇒ {A, B, C}
│         └── D2 ⇒ {B, E}          ← B 被两种拆法共用，只证一次
│                  C ──┬── D3 ⇒ {C1}
│                      └── D4 ⇒ {C2, B}
├─ 分支 main        路线 {T: D1, C: D3} + main 上的蓝图节点
├─ 分支 strategy-2  路线 {T: D2}        + strategy-2 上的蓝图节点
└─ 形式化证明：某个分支的路线闭合 → LeanGround 组装出无前提的认证
```

为什么不让每个分支各存一份图？原因有三：

- **分解是递归的**：根有 2 种拆法、每种下面 3 个子目标各有 2 种时，完整组合就有 2×2³ = 16 种 [推断：组合计数]，
  所以用分支只能表达顶层选择；
- **进度要共享**：各存一份时，一个分支证出的引理，其他分支还要手动导入；
- **认证只追加、按 GoalKey 合并**，天然没有冲突。各存一份可变文档，就把合并冲突又引了回来。

子目标上的替代拆法不需要开分支，作为目标上的并列选项存在即可。只有替代方案大到需要单独写蓝图、单独组织人力时，才开分支。

**路线的语义**：

- 已选择的目标，严格使用所选的认证；
- 未选择的目标，在启用的认证里自动选，前提少的优先；
- 节点转换或重新提交时得到的认证，自动成为该分支在这个目标上的选择；owner 可以改。

**目标状态与路线状态不同**：目标状态（`insufficient` / `derivable` / `certified`）各分支共享，表示存在某种组合
能证出它；路线是否闭合是每个分支自己的。界面分别显示这两者。

### 2.4 大规模协作的原则

1. **人的审阅只花在机器替代不了的地方。** 组装会把整条路线从头检查，所以证明写得对不对不需要人看。必须由人看的只有两件事：
   - 根陈述（及其用到的定义）是否忠实表达了要证的数学。这是唯一的信任根，开局就冻结。
   - 拆法是否值得做。草图检查只保证「子目标全真 ⇒ 目标真」，不保证子目标为真，也不保证子目标更容易。
     拆法新引入的定义不需要做忠实性审阅（最终组装的结论是根陈述）[推断]。
2. **拆法有生命周期，类似合并请求（PR）**：`proposed` → `active` → `paused` / `retired` / `refuted`。
   新拆法默认 `proposed`，未经审阅不参与调度（项目决定 B）。项目阶段 3 已实现（§3.5）；`refuted` 在阶段 5 实现（§3.7）。
   模块模式的项目例外：新拆法直接是 `active`，owner 可以事后暂停或撤下（`docs/module-certification.md` §6 决定 4，2026-10-15）。
3. **证否是必需品。** 证出 ¬P 后，含 P 的拆法自动标为 `refuted`。项目阶段 5 已实现，由 MathDoc 解析 ¬P，不需要 LeanGround 改动（§3.7）。
4. **共享失败记忆。** LeanGround 按设计不保存失败尝试；协调层给每个目标挂尝试笔记（试了什么、卡在哪个证明目标）[推断：对 Agent 群体最省预算]。项目阶段 3 已实现（§3.5）。
5. **租约只用来减少重复，不是独占权。** 过期后才交上来的正确证明照样接收（已实现）。
6. **形式图由认证推导，不手工维护。** 「且」边来自草图的前提；手工维护的依赖边只保留给非形式化的知识依赖。
7. **调度信号来自图**：被多少条路线需要、所在路线离闭合还差多少、已失败几次。项目阶段 5 已实现（`mdc next`，§3.7）。

### 2.5 `mdc` 的角色

**`mdc` 是所有执行者共用的唯一「动作面」。** 执行者包括 Codex、Claude Code、脚本、命令行里的人，以及以后的浏览器侧栏 Agent。
它把协作协议的细节（修订号、幂等键、租约续期、GoalKey 解析）封装成数学工作流层面的动词，地位类似 GitHub 协作里的 `gh` 加 `git`。

它不做四件事：裁判（由 LeanGround 负责）、事实来源（以服务端看板为准）、证明搜索（由 Agent 负责）、维护者决策。

**现状** [实测：读代码，2026-10-08，分支 `claude/mdc-verbs`]：
- 文档命令与 `proof env/submit/list/status/command` 仍是 HTTP API 的薄客户端。其中 `proof command` 读原始 JSON；
  阶段 6 之前它每次都生成新的幂等键，所以断网重试会重复提交。
- 第一批动词 `pull / prove / split / done` 已在项目阶段 2 实现（§3.4）：它们封装了修订号、幂等键、续租和 GoalKey 解析；
  拆法产生的子目标由服务端自动登记陈述，不再需要手写。
- 项目阶段 3 加了 `mdc note FILE|GOAL -m 文字` 和 `mdc done --note`；`split --wait` 报告拆法的状态（通常是 `proposed`）。
- 项目阶段 6 加了读目标的 `mdc goals`、`mdc goal`，维护者用的 `mdc review`、`mdc pick`、`mdc branch new --pick`；
  `proof command` 和这些维护者命令回复丢失后重跑只生效一次（§3.8）。

**动词层**（项目阶段 2）：在现有命令之上，加一层以证明工作流命名的命令。第一批：

| 动词 | 做什么 |
|---|---|
| `mdc pull GOAL [--branch B]` | 领取目标，写出工作文件（§4.11）；之后的 `mdc` 调用顺带续租（项目阶段 2 决定 1） |
| `mdc prove FILE` | 把文件作为完整证明提交 |
| `mdc split FILE -m 说明` | 把文件作为拆法提交；服务端自动为新子目标登记陈述 |
| `mdc done [--spent N]` | 结束租约并报告实际花费 |

之后的动词：

- `mdc check FILE`：只检查不入库，等 LeanGround 提供接口（项目决定 E）；
- `mdc goals`、读取单个目标（`mdc goal`）、维护者用的 `mdc review` 和 `mdc branch new --pick` 已在阶段 6 实现（§3.8）；
  `mdc next`、`mdc refute` 已在阶段 5 实现。

工程性质：

- 默认输出 JSON，错误码稳定；失败时 stderr 输出一行 JSON `{reason, status?, details?, uncertain?}`；
- `.mdc/` 只保存重放记录，不保存令牌；
- 每个 Agent 使用自己的委托子令牌（阶段 4 已实现：`mdc token new/list/revoke`）；
- `mdc mcp` 把同一组动词暴露为 MCP 工具（MCP 即 Model Context Protocol，让聊天式 Agent 调用外部工具的标准协议；阶段 4 已实现）。

**浏览器侧栏 Agent 暂缓实现**（项目决定 F）。以后实现时遵守三条约束：身份是用户的委托子令牌，工具只有 `mdc` 动词，
维护者级操作只生成待确认按钮。

### 2.6 已决定事项

下面按时间汇总所有已经定下的事项。各组编号相互独立，引用时带上组名，例如「合同决定 C」「项目决定 A」。

**迁移的基本决定**（2026-09-28）：

- MathDoc 是顶层协作应用；
- 后端改为 TypeScript，以 `coordinator/` 为基础，并保留完整的知识编辑界面 `web/`；

- 本地 Lean 移出默认路径，不涉及 EvoHarness；
- 顺序是先隔离，再切换默认入口，最后清理。

**合同决定 A–D**（2026-09-29，编码进 v1 合同，§4.6）：

**阶段 4–5 的实现选择与维护者决定**（2026-09-29）：

- 节点与定义 ID 的对应存在 PostgreSQL，不写进块 metadata。原因：写 metadata 会改变节点修订号，让正在编辑的人遇到冲突。

- 自阶段 4 起不再维护旧 Rust 应用的兼容；旧 Rust 代码直接删除，另写一个薄的 TypeScript 版 `mdc`。
- 切换默认入口之前，先在 Mathlib 基座上验收。

**工作文件决定 G1–G4**（2026-10-01，§4.11）：

- G1：未被引用的可用前提，提交时自动删去；
- G2：尝试笔记放进文件的只读前段；
- G3：生成的注释用英文；
- G4：一个文件只对应一个目标。

**项目阶段 1 实现中定下、待评审的细节**（2026-10-02）：

1. 创建项目只限数据库 owner；挂载分支需要该分支的 editor 权限。
2. 分支一律从项目根节点（按 UUID）转换。分支上的根解析出不同的 GoalKey 时，以 `root_statement_differs` 拒绝，不提交任何认证。
3. 看板可见性以 `main` 的读权限为准，读不到的分支及其组装记录不返回。
4. 节点转换或重新提交得到的认证，自动成为分支的选择。
5. 本分支没有转换某节点时，借用另一个已挂载分支上文本相同（含所用定义）的同一节点的状态。
6. LeanGround 项目 ID 随机生成；环境改回以前的值时，恢复那时的看板。

**项目阶段 2 实现中定下、待评审的细节**（2026-10-08）：

1. **续租**：每次运行 `pull / prove / split / done`，都顺带为本工作区内、本人持有、剩余时间不足一半的租约续租；
   是否已过期由服务端判断。不启动常驻进程。`pull` 的 `--ttl` 默认取上限 3600 秒。即 §2.7.2 关键设计 1 的第一种做法。
2. **预算**：`pull` 默认预留 0（`--allocation N` 可改），所以 `done --spent` 默认 0。外部 Agent 的花费只能自报（§4.8）。
3. **拆法说明**：`split` 必须带 `-m`；最长 2000 字符；同一条认证保留第一次的说明。
4. **结论签名的来源**依次是：分支 B 上转换后未改动的节点；看板上记录的声明；只有命题时写成 `theorem goal_<前 8 位> : 命题`。
   看板上的声明合并了 §2.7.2 原计划的第二、三种来源：它取自引入该目标的草图占位，或任一分支上陈述该目标的节点，先记下的保留。
5. **定义 ID 的来源**：目标上只记录 LeanGround 报告的定义 ID，即 `resolve` 响应中被陈述引用的定义、本项目认证的 `definitions`、
   本项目节点登记的定义；不记录请求里给出的定义 ID。原因：目标草稿返回定义源码，而 GoalKey 不受未引用定义的影响，
   如果照抄请求里的 ID，成员就能借一个 `resolve` 读到协调服务可见、但属于其他项目的定义源码。GoalKey 只取被引用的定义
   [实测：读 LeanGround `fact_components.py:93-97`]；这个风险也在本机 LeanGround 上复现过：把代码改回照抄请求 ID 后，
   另一个项目的定义 ID 被 `resolve` 接受并记到了目标上 [实测，2026-10-08，§3.4]。
6. **自动陈述失败的处理**：LeanGround 拒绝或 GoalKey 不一致，只记在作业结果上；LeanGround 暂时不可用时，整个 `submit` 作业重试，
   重试会再提交一次同样的源码。
7. **工作文件前段的上下文顺序**改为 LeanGround 构造检查前言的实际顺序（§4.11），修正原规范中未核实的写法。
8. **租约不独占**：他人持有任务时，`pull` 以 `task_unavailable` 拒绝，并给出持有人和到期时间；`--no-claim` 只写文件、不领取。
9. **工作区记住服务器**：`.mdc/workspace.json` 记录服务器地址，在工作区内运行动词时可以不设 `MDC_URL`；
   设了而不一致时拒绝（`workspace_server_mismatch`）。

**项目阶段 3 实现中定下、待评审的细节**（2026-10-08）：

1. **默认状态**采用 §2.7.3 的倾向：完整证明直接 `active`；从文档节点（挂载、重新提交）来的草图 `active`；
   其余草图（`submit`、`import`、同步时发现的）`proposed`；前提含结论自身的认证到达即 `retired`（记 `retired_reason`）。
   同步时发现、没有经 MathDoc 提交的草图也是 `proposed`，因为不知道是谁写的。
2. **只对项目看板审阅**：没有 `project` 的原型看板与旧请求看板一律 `active`，行为不变。已有的认证保持原状态。
3. **审阅只限 owner**，不设审阅者名单；`decomposition` 命令带可选 `comment`，看板在认证上记最后一次审阅
   （`review`：谁、何时、改成什么、意见）。任何状态都不能改回 `proposed`。
4. **审阅策略**：新命令 `policy {review: required | none}`，只限 owner、只限项目看板；字段缺省视为 `required`（项目决定 B）。
   改成 `none` 只影响之后到达的认证。
5. **笔记的读取**：§2.7.3 说「`mdc show` 也显示」，但 `mdc show REF` 已是显示文档节点的命令。本阶段不新增读取命令：
   笔记在 `pull` 写出的文件前段、界面任务板和看板 JSON（`mdc proof status`）里可见。
6. **笔记的位置**：挂在目标上（`goals.KEY.notes`），与看板原有的项目备注 `notes` 分开；每条记操作者、时间，
   来自 `finish` 的另记尝试 ID。`mdc note` 的幂等键由目标和文字决定（不含修订号），所以回复丢失后重跑只记一条；同一 Agent 有意再记一条相同的笔记也会被当作重放。
7. **界面**：「被几条路线需要」按分支计算：从根出发、只经 `active` 认证、在已选择的目标上只走所选认证，能到达该目标的分支。
   任务板把这样到不了的目标标为 inactive，并禁用领取；`proposed` 的认证不显示「Use on this branch」。

**项目阶段 4 实现中定下、待评审的细节**（2026-10-08）：

1. **子令牌默认只有 `work`**，不给 `edit`（§2.7.4 的待定项，按倾向定）。
2. **各命令所需的权限范围**：§2.7.4 只列了 `work` 的一部分，其余这样定：`sync`、`import`、`submit_node`、项目备注 `notes` 属于 `work`；
   `attach` 属于 `edit`（它要求分支的 editor 权限）；`policy` 与其他 owner 命令属于 `maintain`；`accept` 会写文档，要 `maintain` 加 `edit`。
3. **文档接口与目录操作的权限范围**：分支接口里 read、history、export 之外的动作和分叉分支要 `edit`；目录操作中 `new_branch` 要 `edit`，
   `init`、`remove`、`delete_branch`、`grant`、`set_owner` 要 `maintain`；设置证明环境要 `maintain`；
   通过 `POST /projects` 挂载分支要 `edit`，建项目另要 `maintain`。管理员权限要求主身份是管理员且令牌有 `maintain`。
4. **只有本人令牌能管理子令牌**：子令牌不能再创建、列出或撤销令牌（`own_token_required`），所以权限不能借子令牌扩散。
   主身份从 `MDC_ACTORS` 删除后，它的子令牌一律无效。
5. **令牌格式与存储**：`mdct_` 加 32 字节随机数（base64url）；数据库只存 SHA-256；同一主身份下未撤销的令牌名字唯一，
   过期但未撤销的令牌仍占着名字。
6. **`MDC_ACTORS` 的名字不得含 `/`**：`/` 用来分隔主身份和令牌名，否则名为 `alice/x` 的操作者会被当成 alice。服务启动时检查。
7. **`/api/me`** 增加 `principal` 和 `scopes`；界面按主身份和 `maintain` 判断是否显示 owner 操作。
8. **`mdc mcp`** 手写了 MCP 的标准输入输出传输（逐行 JSON-RPC 2.0），没有引入 MCP SDK 依赖；工具是 `pull`、`prove`、`split`、`done`、`note`。
   工作文件和 `.mdc/` 记录放在服务自己的目录里，`prove`/`split` 只接受 `pull` 给出的文件名。工具失败时返回 `isError` 的结果，不返回协议错误。
9. **预算**：看板数据本来就按完整身份记录尝试，界面在任务板上按身份汇总花费和预留额，服务端没有另存汇总。
10. **LeanGround 侧不变**：`caller_ref` 仍是作业 ID，没有写入 Agent 身份；Agent 的来源只记在 MathDoc。

**项目阶段 5 的维护者决定**（2026-10-08，开始前定下）：

- 负载测试的规模：k = 20 个并发 Agent，n = 1000 个目标；每条命令的端到端延迟目标 p95 ≤ 500 ms。
- 证否由 MathDoc 解析否定：用 LeanGround 现有的 `resolve` 解析 `¬ (P 的命题)`，得到 ¬P 的 GoalKey；不需要 LeanGround 新增 `negates` 字段。
  GoalKey 由 elaboration 决定，不比较文本，所以不违背 §2.7.5 对文本比较的顾虑。
- 只在测量不达标时拆表。

**项目阶段 5 实现中定下、待评审的细节**（2026-10-08）：

1. **拆表范围**：基线不达标（§3.7），所以拆表，但只拆了变化最频繁的任务（`mdc_task`）和尝试（`mdc_attempt`），每行存原对象的 JSON；
   看板其余部分（目标、认证、分支、组装记录）仍是一行 JSONB。看板行另有一个小的 `meta` 列，存租约路径与权限检查要读的字段。
   读看板时把任务与尝试组装回原来的 `Board`，所以领域逻辑、接口返回的结构和界面都不变。
2. **两类命令不比较修订号**：`claim`、`heartbeat`、`finish`、`submit`、`resolve`、`import`、`sync`、`submit_node`、`note`、`negate`
   按服务端当前状态校验，可以用 `If-Match: *`，重放只按请求体匹配。其中除带笔记的 `finish` 和 `note` 外都不写看板行，
   租约命令也不改看板修订号（事件照常逐条记录）。其余命令仍要求修订号，用 `*` 时返回 `428 revision_required`。
3. **并发规则**：`claim` 在项目级 advisory 锁下串行，保证预留不超预算，并在领取前回收到期的租约；`heartbeat` 只锁自己的尝试行；
   `finish` 锁尝试行和任务行。写看板的路径先取项目锁、再锁看板行和未结束的尝试，所以不会与租约命令交错写同一行。
4. **花费由已结束的尝试求和得出**，看板不再存 `spent`。
5. **空同步不改修订号**：作业写回时，看板除 `last_sync` 外没有变化，就只保存，不加修订号、不记事件。否则每 15 秒一次的同步会让
   owner 在界面上的操作频繁冲突（§3.7「过程中修正的问题」）。
6. **同步的另两处优化**：校验认证不再复制整张看板（新函数 `checkFact`）；整批吸收后只重算一次目标状态。这两处不在 §2.7.5 的计划里，
   是测量中发现的（§3.7）。
7. **证否**：看板新增 `negations`（否定目标 → 被证否的目标）。否定目标名为 `not_<名字>`，陈述写作 `¬ (命题)`；
   在被证否目标仍值得做时可以领取。只有否定目标的完整证明触发证否，草图不触发。被证否的拆法不能再启用。
   取消任务时，进行中的租约以 `cancelled` 结束，按预留额计费（与移出成员时相同）。「通知提交者」实现为在相关目标上自动留笔记（操作者记为 `mathdoc`）。
8. **`next` 的候选**：只取拆解前沿上的目标，即被需要、未证出、本身没有生效拆法的目标；否则根定理总会排在最前。
   失败次数取结果为 `no_progress`、`execution_failed` 或租约过期的尝试，不另计笔记。否定目标继承其目标的分数。
   分数相同时，失败少的在前，再按 GoalKey 排序。
9. **界面**：任务板按 `next` 的顺序排列并显示名次；拆法页显示 `refuted` 及原因；命令被拒时，刷新不再清掉错误信息。

**项目阶段 6 实现中定下、待评审的细节**（2026-10-09）：

1. **读视图在服务端计算**：新路由 `GET /projects/ID/goals`、`/goals/KEY`、`/decompositions`，与 `next` 一样由服务端算，
   并且按读者能看到的看板计算，读不到的分支不出现在「需要它的分支」和选择里。「被哪些分支需要」与界面的算法相同：从根出发，只经 `active` 认证，
   在已选择的目标上只走所选认证。
2. **认证的引用**：完整 ID 或至少 8 位的唯一前缀；`pick` 只在该目标的认证中查找，所以别的目标的认证在发送前就以 `unknown_certificate` 拒绝。
3. **选择的权限**：owner（令牌要有 `maintain`），或对该分支有写权限的成员（令牌要有 `edit`；owner 的令牌没有 `maintain` 时也走这条）。
   文档角色由 HTTP 层检查，结果以 `Grants` 传入领域函数，所以领域函数里仍有「非 owner 必须有写权限」这一条，而不是只靠 HTTP 层。
4. **重放日志**：只重发「已发出、没收到回复」的记录；收到回复后再运行同一条命令是新命令。这与 `prove`/`split` 不同（它们对同一文件默认报告上一次提交，
   `--again` 才重发），因为维护者命令常常是有意重复的（例如再次 `sync`），而重复提交证明会浪费 LeanGround 的检查。
5. **`branch new`** 只在带 `--attach` 或 `--pick` 时挂到项目，不带时行为不变。
6. **LeanGround 超时**：运行 Lean 的四类调用默认 960 秒（`LEANGROUND_TIMEOUT_S`，30 秒到 1 天），其余 30 秒；
   超时的错误码是 `leanground_timeout`，连不上仍是 `leanground_unavailable`，两者都可重试。
7. **作业退避**：可重试的失败按 5 × 3^(n−1) 秒、最长 900 秒的间隔，最多 8 次（`JOB_TRIES`）。
8. **TerminusDB 重发**：只对响应中含「Transaction retry count exceeded」的 5xx 重发，最多 3 次，间隔 100 × 2^n 毫秒加最多 100 毫秒抖动。
9. **部署包里的 `mdc`**：§2.7.7 原计划只把工作动词放进一次性容器。实现时发现按第一个参数判断命令会被 `-p` 等标志打乱（§3.8），
   所以改为所有命令都在一次性容器里运行：共用 runtime 的网络命名空间、以调用者的 uid 运行、挂载当前目录；文件参数因此是当前目录下的路径，
   不再是容器内的路径；维护者命令的重放日志放在部署目录的 `state/`。
10. **界面**：对当前分支有写权限的成员也显示「Use on this branch」和「Unpick」；角色取自目录接口 `/api/projects`。
11. **看板是否改变按键排序后的 JSON 比较**（使用演示后补，§3.8 末）：jsonb 会重排对象的键，所以同一个值读回来和再次收到时键序不同，
    不能算改变；任务行与尝试行是否写回也按同样的规则比较。
12. **界面发命令**：按当前状态校验的命令带 `If-Match: *`；其余命令遇到 `revision_conflict` 时读取最新修订号、用同一个幂等键重发，最多 3 次，
    与 `mdc` 一致。被拒命令的错误一直显示到下一次命令或手动关闭，定时刷新只清除加载错误。
13. **节点状态 `registered`**：定义节点没有目标，已登记时显示 `registered`（附定义 ID），被拒时仍是 `rejected`，其余显示 `not_submitted`。
    回写新建的节点（没有节点的前提和定义）按写入的内容记为该分支已转换的节点，所以立即显示其目标的状态或 `registered`。

#### 2.7.1 已完成阶段的计划

#### 2.7.2 阶段 2：`mdc` 动词层

一个 Agent 只用 `pull / split / prove / done` 就能把一个目标拆开并证完；断网后重试不会重复提交。服务端按目标生成工作文件的材料，

#### 2.7.3 阶段 3：审阅

未经审阅的拆法不参与调度：`proposed` 的拆法不产生可领取的任务，启用后才产生；失败的经验以尝试笔记留在目标上。报告见 §3.5。

#### 2.7.4 阶段 4：Agent 身份

每个 Agent 进程用自己的委托子令牌，审计和预算可以区分到具体 Agent，令牌的权限范围可以收窄；`mdc mcp` 把动词暴露为 MCP 工具。报告见 §3.6。

#### 2.7.5 阶段 5：规模与证否

在定下的规模（k = 20、n = 1000、p95 ≤ 500 ms）下延迟可以接受；错误的子目标能被证否并自动停止相关调度；`mdc next` 给出最该做的目标。
证否由 MathDoc 解析 ¬P，不需要 LeanGround 改动（§2.6 项目阶段 5 的维护者决定）。报告见 §3.7。

#### 2.7.6 顺序与依赖

阶段 3、4 依赖阶段 2（审阅要显示拆法说明，`mdc mcp` 暴露的就是阶段 2 的动词）；阶段 5 在拆表前先测量；阶段 6 在 1–5 之后，由维护者从 §5 的缺口中选定。

#### 2.7.7 阶段 6：维护者工作流与部署稳健性

**目标**：维护者和 Agent 只用 `mdc` 就能完成日常协作：看目标、审阅拆法、开一条路线分支、改选择；维护者命令断网重试不会重复生效。
部署后的系统在 LeanGround 重启、短暂中断和 TerminusDB 并发写入时不需要人工处理，并在导出的部署上用真实 LeanGround 走通一遍证明流程。

**现状** [实测：读代码、`gh run list`，2026-10-09]：

- 读目标只能读整张看板 JSON（`mdc proof status`）；审阅、选择只能用 `mdc proof command` 手写命令 JSON。
  `proof command` 每次生成新的幂等键，所以回复丢失后重跑会再生效一次。
- `pick` 只限 owner，分支的 editor 不能改自己分支的路线。
- 协调层访问 LeanGround 的每个请求都是 120 秒超时，而 LeanGround 自己对单个请求的默认上限是 900 秒（`--timeout-s`）。
  所以一个合法但超过 2 分钟的检查一定失败；服务刚启动、Mathlib 还在导入时，请求也会超时（§3.7 末）。
- 可重试的作业失败最多重试 5 次、每次间隔 5 秒，所以 LeanGround 中断超过约半分钟，作业就永久失败 [推断：按 `store.fail` 的规则计算]。
- TerminusDB 在多个事务同时写系统库时会返回 500「Transaction retry count exceeded」（§3.10）；CI 逐个运行测试文件，所以没有遇到。
- CI（`Release check`：原生测试与容器冒烟测试）在每次推送到 GitHub 时运行，已运行 3 次、全部通过。§5 原来说「没有运行过」，已过时。
- 容器冒烟测试把 worker 指向一个不可达的地址，所以导出的部署从未连真实 LeanGround 运行过。部署包里的 `mdc` 包装脚本在 runtime 容器里
  执行命令，所以 `mdc pull` 写出的文件落在容器里，宿主机上的 Agent 用不了工作动词。

**一、`mdc` 与维护者工作流**

| 改动 | 要点 |
|---|---|
| `mdc goals [--status S] [--branch B]` | 新路由 `GET /projects/ID/goals`：每个目标一行，含陈述、状态、哪些分支的路线需要它、各状态的拆法个数、任务状态与持有人、笔记数、失败次数、是否被证否 |
| `mdc goal GOAL` | 新路由 `GET /projects/ID/goals/KEY`：一个目标的全部信息，包括陈述与声明、笔记、以它为结论的认证（状态、前提的陈述与状态、说明、提交者、最后一次审阅、被证否的原因）、各分支在它上面的选择、任务与尝试、否定关系。`mdc show` 已是显示文档节点的命令（§2.6 项目阶段 3 决定 5），所以叫 `goal` |
| `mdc review` | 不带参数时列出待审阅（`proposed`）的拆法，附前提的陈述、说明、提交者、需要它的分支；`mdc review CERT --accept\|--pause\|--retire [-m 意见]` 发送 `decomposition` 命令 |
| `mdc pick GOAL CERT\|auto [--branch B]` | 设置分支在目标上的选择；`auto` 取消选择，恢复自动选 |
| `mdc branch new NAME --pick GOAL=CERT …` | 建文档分支，挂到项目看板，等转换作业结束，再逐个设置选择。必须等转换结束，因为转换会按节点重新推导选择（`derivePicks`），先设的选择会被覆盖 [实测：读 `worker.ts`] |
| 分支 editor 改本分支的选择 | `pick` 改为允许 owner，或对该分支有写权限的成员。文档角色在 HTTP 层检查（与 `attach` 相同），领域函数只检查成员身份；令牌范围上，owner 用 `maintain`，editor 用 `edit` |
| 维护者命令可安全重放 | `review`、`pick`、`proof command` 发送前把（幂等键、修订号）写进本机日志，日志不含令牌。回复丢失后重跑同一条命令，就用同一个键和修订号重发；服务端先查键，所以只生效一次。已收到回复后的重跑算新命令。日志放在 `$XDG_STATE_HOME/mdc`（默认 `~/.local/state/mdc`），因为这些命令不一定在工作区里运行 |

认证的引用方式与目标相同：完整 ID，或至少 8 位的唯一前缀。

**二、部署与稳健性**

| 改动 | 要点 |
|---|---|
| LeanGround 超时按操作区分 | 要运行 Lean 的调用（`resolve`、`submit`、`define`、`assemble`）默认 960 秒，比 LeanGround 的 900 秒默认上限略长，可用 `LEANGROUND_TIMEOUT_S` 修改；其余调用（读取、查询、事件、基座）30 秒。HTTP 请求中只有读取类调用，所以界面不会被长超时卡住。超时的错误码改为 `leanground_timeout`，与连不上（`leanground_unavailable`）区分，两者都可重试 |
| 作业重试退避 | 可重试的失败按 5 秒、15 秒、45 秒……指数退避，单次间隔最长 15 分钟，最多 8 次，合计约 40 分钟 |
| TerminusDB 冲突重试 | 「Transaction retry count exceeded」表示事务整体没有提交 [推断：TerminusDB 的乐观事务重试用尽后回滚]，所以客户端对任何请求都最多重发 3 次，间隔递增 |
| 部署包的 `mdc` | 工作动词（`pull`、`prove`、`split`、`done`、`note`、`refute`、`next`、`mcp`）改在一次性容器里运行：挂载当前目录，以调用者的 uid 写文件，经内部网络连 runtime；其余命令仍在 runtime 容器里执行 |
| CI | 改正 §5 的说法；本阶段新增的测试都不需要 LeanGround，随 CI 运行 |

**验收**：

1. 只用 `mdc`：owner 列出目标、读一个目标、把一个 `proposed` 拆法审阅为 `active`；用 `branch new --pick` 开一个选用另一种根拆法的分支，并在该分支上组装成功。
2. 该分支的 editor（成员、不是 owner）能改它的选择；对它只有读权限的成员被拒（403）；editor 改不了别的分支。
3. `review`、`pick`、`proof command` 在「请求已到达、回复丢失」后重跑：看板只变一次（一条事件，修订号只加一）。
4. LeanGround 刚重启时立即运行真实 LeanGround 的测试，全部通过，不需要人工预热。
5. 作业执行中 LeanGround 停止，恢复后作业自动完成（在替身上测）。
6. TerminusDB 的冲突错误被重试（单元测试）；按默认并发运行全套测试多轮，不再出现该失败。
7. 用本阶段代码构建的镜像导出部署（不含源码），连真实 LeanGround：owner 建项目，Agent 在宿主机目录里用 `./mdc pull / prove / done`
   证完根目标，owner 组装并接受，证明写回分支文档。

**不在本阶段**：worker 一次只执行一个作业，长时间的 Lean 检查会挡住其他项目的作业；`mdc check`（等 LeanGround 接口）；界面上的令牌与成员管理。

**使用演示中发现并修正的缺陷**（2026-10-09）

  - **API 服务收到 SIGTERM 后不退出**：本机留着 9 个这样的进程，每个带 2–4 个 LaTeX 渲染子进程。
    原因是停止时只关了 HTTP 服务和连接池，渲染子进程的管道让事件循环一直不结束；它们多数是浏览器 e2e 测试启动后留下的。
    改为 HTTP 服务关闭时停掉所有渲染进程。演示服务上先启动 2 个渲染进程再发 SIGTERM（n = 1），约 0.4 秒退出，没有遗留渲染进程。
  - **网页没有退出登录**：只有收到 401 时才会清掉令牌，换身份只能手动清浏览器存储。现在两个页头都显示当前身份和「Sign out」。
  - **`mdc goals` 显示的名字，`mdc pull` 不认**：一个还没有节点的目标（例如 split 新加的前提）只能用 GoalKey 前缀。
    现在找不到节点时按 `mdc goals` 显示的名字查找，同名时报 `ambiguous_goal`。
  - **已经写回的组装仍显示「Accept and write back」**：再点一次不会重复写入（写回批次的编号由组装决定），但容易误导。
    现在显示「Written back to branch …」。
- 测试：服务进程停止 1 项（启动真实的 `serve` 子进程和替身渲染器）、目标名查找 1 项、`maintain` 中改用名字领取、
  前端「已写回」判断 1 项、e2e 中的退出登录与已写回显示。撤掉服务停止和名字查找的修正时，对应测试失败（2 处变异）。
  协调层 68 项（连真实 LeanGround）、前端单元测试 37 项、浏览器 e2e 15 项全部通过；e2e 跑完后没有遗留 API 服务。
- 结论：这 4 处都已修正并有测试守住。
- 未覆盖：
  - 9 月 29 日留下的 6 个旧进程没有清理。
  - 以下 2 点按设计如此，没有改：
    - 根定理已证完时，`mdc next` 不再推荐目标，而 `mdc goals` 的 `needed_by` 仍列出路线能走到的分支；
    - 回写只添加依赖边，所以 `alt` 上的 `double_add` 改用 `double_comm` 后仍显示依赖 `double_eq`。

**动手课中发现并修正的问题**（2026-10-10）

- 目的：维护者自己动手走一遍"分解、证明、组装、写回"时，修正 1 个缺陷，实现记下的 2 条待办。
- 背景：数据库 `lesson`，只用 owner 一个身份，审阅已关闭；根定理 `triple_add_zero`，中间引理 `triple_eq`。
- 结果 [实测]：
  - **证明被拒时看不到原因**：用 `rfl` 证 `triple_eq` 被 LeanGround 拒绝，`mdc prove --wait` 只给出 `verification_failed`。
    LeanGround 的拒绝响应是 `{kind, reason, error}`，Lean 的报错在 `error` 里；协调层只保留了 `reason`。
    现在报错存进作业的 `details`（新列，最多 8000 字符）、被拒节点绑定的 `details` 和失败组装的 `details`；
    `mdc prove/split` 的输出多一项 `messages`，并把报错原样打印到标准错误；协作窗口的「Recent failures」、组装记录和节点状态灯的悬停提示也显示它。
  - **待办：`mdc status` 不显示当前身份和默认分支**：输出改为 `{actor, project, server, projects}`。
  - **待办：「on route」的含义和字面不一致**：原来标的是"被某次已通过的组装用到过"，与当前分支的选定无关。
    现在按协调层组装时选路线的同一规则（选定优先，其余前提少者优先、再按 ID）算出当前分支的路线，标为「on 分支's route」。
- 测试：被拒证明带回 Lean 报错 2 项（LeanGround 替身用 `-- wrong:` 注释模拟拒绝；真实 LeanGround 上用 `rfl` 证 `n + n = 2 * n`），
  `mdc status` 断言 1 处，前端路线选择 1 项，e2e 中断言「on main's route」恰好标出 2 张证书。
- 结论：3 处都已实现并有测试守住。
- 未覆盖：失败组装的 `details` 没有测试，因为替身的组装总是通过，真实 LeanGround 上也很难构造组装失败；
  前端的路线选择是协调层 `selectRoute` 的复制实现，两边只靠同样的规则和各自的测试保持一致。

## 4. 技术细节

### 4.1 架构与部署

```
web/（知识编辑界面 + 协作视图）
  │  /p/<库>/<分支>/api/...          /api/coordination/...
  ▼
coordinator/（TypeScript；三种模式 migrate / serve / worker）
  ├─ 文档接口 ──────────► TerminusDB（文档、依赖、历史）
  ├─ LaTeX 预览 ────────► renderer/renderer.py 常驻进程（plasTeX）
  ├─ 协作接口 + 作业 ───► PostgreSQL（工作区、环境、看板、命令、事件、作业）
  └─ worker 作业 ───────► LeanGround 事实接口（/v1/facts/…、/v1/bases/…）
```

- `serve`：一个 HTTP 进程服务所有数据库与分支。分支在第一次请求时加载，之后常驻；每次请求核对 TerminusDB
  的数据版本，只有版本变化时才重新加载。
- `worker`：周期同步与作业执行。可以运行多个；同一项目同一时刻最多只有一个作业在运行，作业的领取会续期，
  崩溃后的作业由其他 worker 重新领取。
- 部署（`compose.server.yaml`）由五个服务组成：
  - `database`（TerminusDB）、`postgres`；
  - 一次性的 `migrate`；
  - `runtime`（API）、`worker`。

  LeanGround 在外部，由 `LEANGROUND_SERVER_URL` 指定。
- 配置项：`MDC_ACTORS`、`MDC_HOST`、`MDC_PORT`、`MDC_TERMINUS_URL/USER/PASSWORD`、`MDC_DATABASE_URL`（及 `MDC_DATABASE_PASSWORD`）、
  `LEANGROUND_SERVER_URL`、`LEANGROUND_FACT_TOKEN`、`LEANGROUND_ACTOR`、`LEANGROUND_TIMEOUT_S`、`MDC_WEB_DIR`；完整列表见文档站
  `reference/configuration.md`。`MDC_POSTGRES_PASSWORD` 只供开发用的 `compose.yaml` 建库，后端不读它。
  机密项都可以改用 `*_FILE` 形式从文件读取；机密放在 `secrets/` 中，镜像以 uid 10001 运行。

### 4.3 身份与权限

- 每个 API 请求都带 `Authorization: Bearer <令牌>`；令牌在 `MDC_ACTORS` 中映射到操作者，不接受请求体自报身份。
  浏览器请求还要求同源。
- **委托子令牌**（项目阶段 4）：身份写作 `alice/codex-1`。文档角色、成员、owner、管理员都按主身份 `alice` 判断；
  租约、事件、提交者、笔记、审阅、文档提交的作者记完整身份。子令牌的权限范围（`work`、`maintain`、`edit`）在主身份的角色之外再加限制，
  不足时返回 `403 token_scope_required`（文档接口返回 403 并写明所需范围）。各命令与接口所需的范围见 §2.6 项目阶段 4 决定 2–3。
- 工作区角色矩阵（合同决定 D）：

| 动作 | 允许的角色 |
|---|---|
| read、history、export | admin、owner、editor、viewer |
| write、branch_create、proof_request_create（提交/挂载分支） | admin、owner、editor |
| branch_delete、import、member_manage（授权、设置证明环境） | admin、owner |
| database_create、database_delete | admin |

- 新分支复制来源分支的授权规则。无权读取与不存在一律返回 404；能读但无权写返回 403。
  没有工作区记录的旧库只有管理员可见，由管理员用 `set_owner` 认领。
- **协作不扩大文档权限**：
  - 项目看板只对能读 `main` 的成员可见，读不到的分支（连同其组装记录）不返回；
  - 创建项目需要 `main` 上的 owner 权限；挂载分支需要该分支的 editor 权限；接受回写需要目标分支的 write 权限；
  - 成员必须能读 `main`。
- **已知限制**：目标和认证属于整个项目。读不到某个分支的成员，仍能看到由它产生的目标标题和认证源码。
  所以需要对部分成员保密的分支，应当放在另一个数据库里。

### 4.4 文档接口

路径为 `/p/<库>/<分支>/api/...`：图查询、节点读写、依赖、LaTeX、历史、导入导出。路由、状态码与旧应用一致：

- 428：缺 `If-Match`；
- 412：修订不符；
- 409：数据版本冲突；
- 422：校验失败。

全局接口 `/api/status`、`/api/projects` 处理目录操作：`init`、`remove`、`new_branch`、`delete_branch`、`grant`、`set_owner`。
没有按分支的启动或停止。分支接口的请求体上限是 256 MiB，协作接口是 2.2 MB。

### 4.5 节点状态的两个维度

`formalization.lean` 表示本地检查，新后端里恒为 `unverified` 或 `no_code`。`formalization.lean_certification`
表示 LeanGround 认证：

| 值 | 含义 |
|---|---|
| `null` | 没有 Lean 块 |
| `not_submitted` | 没有适用于该节点的转换 |
| `insufficient` / `derivable` / `certified` | 目标状态；附 `project`、`branch`（显示的是哪个分支的转换）、`goal`、`minimum_trust`、`checked_at` |
| `stale` | 节点或其陈述所用定义的 Lean 文本在转换后改了 |
| `rejected` | 转换器或 LeanGround 拒绝了它，附原因 |
| `registered` | 定义节点：其定义已在 LeanGround 登记，附 `definition_ids`；定义没有要证的目标。写回提交会把写入的定义标成 `certified`，也算已登记。还在等依赖登记的定义显示 `not_submitted` |

**状态来源的优先顺序**：

1. 本分支在当前项目看板上的转换；
2. 本分支在被取代的项目看板上的转换；
3. 另一个已挂载分支上文本相同（含陈述所用定义）的同一节点；
4. 本分支的旧请求。

[实测：读 `certification.ts`] 本分支有项目看板上的转换（当前或被取代）时，不借用其他分支的状态。

`truncated` 恒为假，因为状态由协作层推导，不调用 LeanGround 的 `query`。

`formalization.lean_role`（`/graph/full` 里也有）说明节点是定义还是定理：先按显示的转换的绑定，未绑定时按 Lean 块的 `lean_role` 元数据，
否则有 theorem/lemma 即定理、只有定义即定义；没有 Lean 块或扫描器读不了时为 null。界面据此把定义显示为 Definition / Registered definition。

### 4.7 节点转换（声明绑定）

挂载一个分支时，从根节点出发，沿依赖收集所有有 Lean 块的节点。没有 Lean 块的节点是非形式化说明，遍历不穿过它们。
逐个节点分类：

| 块内容 | 处理 |
|---|---|
| 只有 `def`、`abbrev`、`noncomputable def`、`structure`、`inductive` | 定义节点：按依赖顺序调用 `define` 登记，得到定义 ID |
| 恰好一条 `theorem`/`lemma`，或 metadata 的 `lean_conclusion` 指定了结论 | 定理节点：带上所用定义的 ID 解析陈述，得到 GoalKey |
| 定理的证明是 `sorry` | 成为开放目标，自动生成证明任务 |
| 定理带证明 | 依赖的定理写成前提占位，放在本节点声明之前一起提交：有前提时用 `lean-worker-sketch`，否则用 `lean-worker` |
| 其他 | 带原因拒绝 |

规则：

- `import` 丢弃；节点里的 `open`、`set_option`、`universe`、`variable` 必须与环境的 context 逐行相等（`local_context_mismatch`）；
- 定义节点不能依赖定理节点；
- 拒绝原因包括 `multiple_conclusions`、`mixed_declarations`、`unsupported_declaration`（instance、class、namespace、属性、`open … in`）、
  `premise_name_collision`、`definition_name_taken`、`ambiguous_binding`、`unregistered_statement_definition`；
- 依赖被拒节点的节点随之被拒，details 写明是哪个节点。

**分支级规则**：

- 根节点不在分支上时，拒绝为 `root_not_on_branch`；
- 根陈述与项目根目标不同时，拒绝为 `root_statement_differs`，而且什么也不提交；
- 所有分支共用一个 LeanGround 项目范围，所以两个分支以同名、不同内容登记定义时，后者得到 `definition_name_taken`。

`submit_node` 重新读取一个节点并提交它当前的证明；节点仍是 `sorry` 时，以 `open_goal` 拒绝。

### 4.8 协作看板与规则

**命令**：`POST /api/coordination/projects/<id>/commands`，带 `If-Match: "<修订号>"` 和 `Idempotency-Key`。
同一个键配同样的请求体，返回第一次的结果；配不同的请求体，返回 `idempotency_conflict`。

| 命令 | 谁 | 作用 |
|---|---|---|
| `claim` / `heartbeat` / `finish` | 成员 / 租约持有人；释放另有令牌背后的本人、带 `maintain` 的 owner | 租约：30–3600 秒；`finish` 报告花费和结果，可带一条笔记。会话没有 `mdc done` 就停下时，它的租约要到期才放开；本人或 owner 可以提前释放（`outcome: released`、`spent: 0`，2026-10-15 3a 试点中补上） |
| `note` | 成员 | 在目标上留一条尝试笔记（1–500 字符；保留最近 50 条） |
| `edit_note`、`delete_note` | 笔记作者（人可以改自己委托令牌的笔记）；`delete_note` 另有 owner | 按 `{actor, at}` 找到一条笔记，改写正文（记 `edited`）或删除；owner 的令牌删别人的笔记需要 `maintain` |
| `submit`、`resolve`、`import`、`submit_node`、`attach`、`sync` | 成员（`attach` 还需要分支的 editor 权限） | 后台作业；`submit` 可带 `description`，吸收草图时为新前提登记陈述（§4.11） |
| `task`、`members`、`decomposition`、`policy`、`pick`、`assemble`、`retry`、`accept` | owner | 管理；`decomposition` 即审阅，可带意见；`policy` 设定新拆法是否等待审阅 |
| `notes` | 成员 | 项目备注 |

**规则**：

- 数学状态、任务、尝试、拆法状态、项目状态分开记录。
- 目标按 GoalKey 去重；每个新目标自动得到一个 `prove` 任务。
- 只有从根出发、经 `active` 认证能到达的目标才能领取（否则 `inactive_goal`）。
- **初始状态**（项目看板，阶段 3）：完整证明 `active`；文档节点来的草图 `active`；其余草图 `proposed`（`policy` 为 `none` 时 `active`）；
  前提含结论自身的认证 `retired`。原型看板一律 `active`。已在看板上的认证重新吸收时保持原状态。
- **租约**：只有一个持有人；epoch 防止迟到者覆盖新状态；过期在下一次状态变化时记录，按预留额全额计费；
  过期只撤销调度权，迟到的正确证明仍然吸收。
- **预算**：领取时预留，结束时结算；超额以 `budget_exhausted` 拒绝。外部 Agent 的实际花费只能靠它自己上报。
- **同步**：每个就绪、未被取代的看板约每 15 秒同步一次：
  - 重新读取已知认证，读不到的标为不可用；
  - 读取 LeanGround 事件，事件与游标在同一事务里保存；
  - 记录到期的租约；
  - 检查各分支是否过期，已删除的分支标为过期。
- 目标状态从认证推导；没有叶子证据的环不能证出任何目标。
- **只读看板**：旧请求返回 `proof_request_read_only`，被取代的看板返回 `project_superseded`；二者都不再同步。
- **修订号**（阶段 5）：租约命令与入队类命令按当前状态校验，可用 `If-Match: *`，不改修订号；其余命令比较修订号。空同步不改修订号。
- **证否**（阶段 5）：`negate` 登记否定目标；否定目标的完整证明到达时，目标被证否，前提含它的认证变为 `refuted`，
  只经由它们到达的目标的任务被取消，相关目标上留下笔记。
- **推荐**（阶段 5）：`GET /projects/ID/next` 按 §2.6 项目阶段 5 决定 8 打分。

**读取**：除看板本身外，`GET /projects/ID/jobs`（最近 100 个作业）、`/jobs/JOB`（单个作业及其 `result`）、
`/goals/KEY/draft`（目标草稿，§4.11）、`/nodes/UUID/draft`（节点草稿）、`/facts/CERT`（认证及源码）、`/next`（推荐，阶段 5）。

### 4.9 组装、回写与过期

**组装**：

- 选路在协作层完成，只用 `active` 的认证；已选择的目标严格使用所选认证，其余选前提最少的；路线不闭合时以 `no_active_route` 拒绝。
- LeanGround 先固定计划，再组装。失败且可重试时，用同一计划重试；换路线就是新计划。组装用的尝试号就是运行 ID，所以响应丢失后可以重放。

**回写**（目标是组装记录所在的分支，其他分支不受影响）：

1. 路线上已有对应节点的，先核对其 Lean 文本仍是转换时的文本，否则整批 `aborted`（`document_conflict`）。
2. 由节点原文转换来的认证只写 metadata；在别处证出的，替换声明部分，保留节点原有的 import 与 context 行，
   且结论名必须保留（否则 `public_declaration_renamed`）。
3. 没有节点的子目标和定义新建节点，节点 ID 由批次 ID 派生，所以重放不会重复创建。
4. 写入的块带 `certification_id`、`certified_lean_sha256` 和批次 ID；根节点记录最终认证。
5. 整批作为一次 TerminusDB 提交，带读取时的数据版本作为前置条件；已提交的批次由根节点上的批次 ID 识别。

**过期**：

- **分支级**：根节点、直接前提或所用定义的 Lean 文本与转换时不同，即为过期，此时 `accept` 被拒（`proof_request_stale`），旧成果保留。
- **节点级**：节点自己或其所用定义的文本改了，就显示 `stale`。
- 回写自己写入的文本是新的基准。
- 已知取舍：前提只改证明、不改陈述时也会判为过期。这是保守的做法，不会错用旧成果。

**环境变化**：环境改了，看板就被取代；改回以前的值，恢复那时的看板。

### 4.10 LeanGround 接口与部署前提

**使用的接口**：

- `POST /v1/facts/{submit,define,resolve,read,plan,assemble,project,widen,events}`；
- `GET /v1/bases/{key}`；
- 模块模式的项目另用 `POST /v1/modules/{shared,resolve,check,submit}`（LeanGround `docs/14`；`docs/module-certification.md` §5.4），
  组装仍走 `/v1/facts/plan` 与 `/v1/facts/assemble`，组件是 `lean-modules`。

**超时与重试**（项目阶段 6）：`resolve`、`submit`、`define`、`assemble` 要运行 Lean，上限默认 960 秒（`LEANGROUND_TIMEOUT_S`），
比 LeanGround 自身的单请求默认上限 900 秒略长；其余调用 30 秒。超时报 `leanground_timeout`，连不上报 `leanground_unavailable`，
两者都可重试：作业按 5、15、45……秒退避，最长间隔 15 分钟，最多 8 次。HTTP 请求里只有读取类调用，所以不会被长上限卡住。

带定义的命题必须用 `/v1/facts/resolve` 并传 `definitions`。定义只通过 ID 传递；新定义经 `new_definitions` 随提交一并登记。
组件与模式必须配对：`lean-worker-sketch` 对 `sketch`，`lean-worker` 对 `leaf` 和组装。

**部署前提**：

- LeanGround 的 `main` 不早于 `3965273`；
- 已执行 `leanground db schema --only 10-definitions`；
- worker 按新版重新安装：旧 worker 拒绝一切带定义的请求，症状是返回 `definition_is_proposition`；
- 草图组件没有被停用；
- 协调服务的身份（`LEANGROUND_ACTOR`）与令牌一致。

**LeanGround 侧的限制**：

- 源码形态较严，拒绝 `#` 命令、`open … in`、属性、`private`、`instance`、`class`、记号、宏等；
- 没有读取项目成员的接口；
- 没有按 GoalKey 读取陈述的接口，认证也只给出前提的 GoalKey，不给出完整身份。所以 `submit` 作业从草图的占位声明重新 `resolve`，
  GoalKey 一致才记下（§4.11）；
- `/v1/check` 按 import 选择基座，不认识项目里登记的定义，也不返回 `sorry` 处的证明目标（所以需要项目决定 E 中的新接口）。

### 4.11 目标工作文件规范 `mdc-goal-file/1`

本节规定 `mdc pull` 写出、`mdc check/prove/split` 读入的文件。规范已定（G1–G4），已在项目阶段 2 实现（`coordinator/src/mdc/`；
`check` 除外）。「必须」「不得」违反时 `mdc` 拒绝；「应当」违反时只警告。

**目标草稿**（`GET /projects/ID/goals/KEY/draft?branch=B[&with=K1,K2]`）：`pull` 只用这一个接口取材料。

- 结论的名字与签名依次取自：分支 B 上绑定该目标、转换后 Lean 文本未改的节点；看板上的 `declaration`（引入该目标的草图占位，
  或某个分支上陈述它的节点，先记下的保留）；看板上只有 `proposition` 时，写成 `theorem goal_<前 8 位> : 命题`。
  目标没有身份时报 `goal_unresolved`，因为没有身份就无法提交它的证明。
- 可用前提：节点来源时取该节点的直接前提节点；再加上 `with` 指定的目标。每个前提的签名按同样的顺序取得。
- 定义：结论与前提所用定义的并集，加上它们的依赖，按依赖顺序排列，源码从 LeanGround 读取。
- 另给出 `root_module`、`context`、`options`、`environment_id`、看板修订号、最近 20 条笔记（新的在前）和该目标的 `prove` 任务及租约。

**新子目标的陈述**：`submit` 作业吸收草图后，对看板上还没有身份的每个前提，按认证的绑定名在提交的源码中找到占位声明，
以 `∀ binders, type` 加上认证的 `definitions` 调用 `resolve`。GoalKey 一致就记下身份、命题、被引用的定义和声明；
不一致记为 `identity_mismatch`，LeanGround 拒绝记为它的原因码，都只写进作业结果。

**工作目录**：

- `.mdc/workspace.json`（服务器地址、项目，不含令牌，令牌一律从环境变量 `MDC_TOKEN` 读取）；
- `.mdc/files/<文件名>.json`（每个工作文件一条记录）；
- 工作文件默认命名为 `<GoalKey 前 8 位>-<结论名>.lean`；目标文件已存在时拒绝覆盖（`file_exists`）。

**文件结构**：

- 文件为 UTF-8；读取时把 CRLF 换行统一为 LF。
- 全文有且只有一行分隔行 `-- mdc: edit below this line`，它是前段的最后一行。前段的 SHA-256 记在 `.mdc/` 中。
- **前段（只读）**，按顺序：
  - 第 1 行 `-- mdc-goal-file/1`；
  - 说明注释；
  - `import <root_module>`；
  - 环境上下文与已登记定义，顺序与 LeanGround 构造检查前言的顺序相同 [实测：LeanGround `Tools/VerifyWorker.lean:272-280`，`3965273`]：
    `raw`、`local_options`、由环境 `options` 生成的 `set_option` 行（按键排序）、`universe`、`open`、已登记定义、`local_notation`、
    `local_attrs`、`variable`。定义按依赖顺序排列，每段前有一行 `-- definition <名字> (<ID 前 8 位>)`。
    原规范写的是 `set_option`、`open`、`universe`、`variable`，并把定义放在上下文之后；那是未核实的推测，已按实际顺序修正；
  - 最近 20 条尝试笔记，用 `--` 注释写出，每条最多 500 字符；
  - 分隔行。
- **正文（可编辑）**，初始内容是可用前提（每行一个 `theorem … := sorry`）和结论定理。顶层命令只能是三类：
  - 结论：恰好一条，签名不得改动；
  - 前提占位：证明体恰好是 `sorry` 或 `by sorry`；
  - 辅助声明：已完整证明的引理，或 `def` 等定义。

正文规则（括号里是 `mdc` 报的原因码）：

- 不得含 `import`、`open`、`set_option`、`universe`、`variable`（`context_in_body`）；
- 不得含 `example`、`instance`、`class`、`namespace`、`section`、`#` 命令、属性、`private`（`unsupported_declaration`）；
- 声明的续行必须缩进；
- 声明名全文唯一（`duplicate_name`），且不含 `'`（`invalid_name`）；
- 结论缺失、重复或签名被改，分别报 `root_missing`、`root_duplicated`、`root_statement_changed`；
- 提交时结论的证明不得是 `sorry`（`root_is_sorry`）；`check` 不受此限；
- 前提占位与结论的签名文本相同时，报 `premise_equals_root`。

**从文件到请求**：

1. 规范化换行；
2. 核对分隔行和前段哈希（`separator_missing`、`prefix_modified`）；
3. 用与服务端同一份扫描器检查正文；
4. 删去拉取时写入、但正文中没有引用的可用前提（G1）。Agent 自己新增的占位不删，交给服务端以 `subgoal_unused` 拒绝；
5. 判断模式：没有占位就是 `leaf`，否则是 `sketch`。`prove` 要求 `leaf`（否则 `has_premises`），`split` 要求 `sketch`（否则 `no_premises`）；
6. 名字出现在某个前提陈述里的定义，列入 `new_definitions`；
7. 组成 `submit` 请求，只发送正文。`--dry-run` 打印实际要提交的源码。

**重放**：

- 发送前，先把幂等键 `submit-<请求 SHA-256 前 32 位>-r<修订号>`、修订号和请求哈希写入记录；
- 结果不确定时，原样重发。服务端先查幂等键、再查修订号，所以第一次如果已经生效，重发只会拿回第一次的结果；
- 收到 `revision_conflict` 时，说明之前的发送没有生效，用新的修订号新增一条记录。

**记录字段**：`format`、`file`（相对工作区根的路径）、`project`（看板 ID）、`database`、`branch`、`goal`、
`environment_id`（环境变了就拒绝提交，报 `environment_changed`）、`root`、`root_signature`、`definitions`、`premises`、
`prefix_sha256`、`pulled_revision`、`lease`（任务、尝试、epoch、持有人、到期时间、ttl、预留额、领取时间）、`submissions`。

**提交记录的状态**：`sending`（已落盘、结果未知）、`queued`（看板已接收）、`certified`（作业已记下认证）、`rejected`（被拒，附原因）、
`not_applied`（修订号过时，没有执行）。同一份正文已有 `queued` 或 `certified` 的记录时，只报告那次结果（`replayed: true`），
`--again` 强制重发；`--wait` 等作业结束（`--timeout` 默认 600 秒）。

**分支**：`pull` 的 `--branch` 默认取 `-p` 指定的分支，决定节点来源的签名和可用前提。
