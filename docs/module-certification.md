# 模块级认证：协作证明以完整 Lean 模块为单位（方案）

状态：2026-10-14 初稿；同日完成阶段 0 原型（§5.1），按结果修订 §2.1、§3.2–§3.4、§4（§8）。2026-10-15 维护者决定 §6 第 1–4 条，
完成阶段 1（LeanGround 组件与接口，§5.2–§5.3）与阶段 2（MathDoc 接入，§5.4–§5.5）。阶段 2 的代码在两个仓库里都未提交，
也都未部署到正式服务。涉及 MathDoc（分支 `codex/mathdoc-coordination`）与 LeanGround（分支 `project-checks`）。
来源标注沿用 `docs/mathdoc.md` §1：`[实测]` 附条件，`[推断]`，`[未验证]`。相关文档：`docs/mathdoc.md` §2.3–§2.4、§4.7–§4.11；
`docs/external-proofs.md`；LeanGround `docs/13`。

## 1. 目的

回答三个问题：

1. MathDoc 现在的协作认证，和 OpenAI `math` 仓库体现的做法相比，问题出在哪里；
2. 能不能保留目标图与认证的含义，同时让每份贡献使用完整的 Lean；
3. 分几步做，每一步怎么验收，要先回答哪些待定问题。

结论：

- **保留**：目标、目标身份（GoalKey）、拆解的且/或结构、路线、目标状态、可信等级、证否、笔记、租约、调度（§3.6）。
- **换掉三件事**：
  - 认证的单位：由「一条声明的源码」改为「一组 Lean 模块」，下文称**贡献**；
  - 检查方式：由「源码形态规则」改为「沙箱里用 Lake 编译，再做常量层检查」；
  - 组装方式：由「源码拼接后整份重检」改为「常量层合并后，从空环境整体重放」。
- **先做原型**（阶段 0，§5），用 Seymour、IMO 029 和 LEAP 的已有材料验证这三件事都成立，再改服务。

## 2. 背景

### 2.1 名词

| 名词 | 含义 |
|---|---|
| 协作认证 | LeanGround 事实层（`/v1/facts/*`）的产出：某个目标在若干前提下成立；可以按目标身份组合 |
| 目标身份（GoalKey） | LeanGround 为一条命题算的指纹。同一命题在不同分支上得到同一个值，所以证一次处处可用 |
| 前提占位 | 证明体恰好是 `sorry` 的引理，代表拆解里待证的子目标 |
| 组装 | 沿一条路线，把各认证接起来，得到一份不依赖任何前提的根定理证明 |
| 冻结目标、连接定理 | LeanGround `docs/13` 阶段 2a（已实现、未部署）：resolve 时保存目标 elaborate 后的完整类型；提交时由服务端加一条「类型 = 冻结类型、值 = 提交的根定理」的定理，交给内核检查 |
| 贡献（本方案新增） | 为一个目标提交的一组 Lean 模块。没有占位就是完整证明，有占位就是拆解 |
| 共享模块（本方案新增） | 新目标的陈述用到的定义所在的模块，可以带引理；整体认证一次（没有根，不许占位），按内容寻址登记 |
| Lake | Lean 的构建工具，按 `import` 依赖顺序编译模块 |
| 内核重放 | 把常量放进环境，重新过一遍 Lean 内核；这是正确性的最终依据 |
| Comparator | Lean 官方（leanprover）的核对工具。它查三件事：证明里的定理与陈述文件完全相同；只用了允许的公理；从空环境重放能通过内核 |
| 沙箱（landrun） | Linux 上限制进程读写与网络的工具。Comparator 用它隔离编译过程，因为编译 Lean 时可以执行任意代码 |

### 2.2 现在的协作认证与它的代价

做法 [实测：读 `coordinator/src/lean-source.ts`、`proof.ts`、`~/imo-run/template/AGENTS.md`、LeanGround `docs/12`、`docs/13`]：

- 一个库对应一条冻结的根定理。
- 节点的 Lean 块只能二选一：要么只含定义，要么恰好含一条定理。`namespace`、`instance`、`class`、`private`、属性、
  `open … in`、`#` 命令都被拒绝。
- **拆解**：写一个证明，把子引理写成 `sorry`。每个 `sorry` 引理都必须被直接用到（`subgoal_unused`），`sorry` 只能是整个引理体
  （`sorry_outside_subgoals`）。
- 每次 `prove` 或 `split` 都排队交给 LeanGround，同一项目串行，单次上限 960 秒。`mdc check` 约 8.5 秒，不留记录。
- **组装**：把选定路线上的源码拼成一个文件，每份放进自己的命名空间，前提改写为对提供者的引用，再整份重检。

代价 [实测，来源依次为 LeanGround `docs/13` §2.2 与 §5.1、`docs/mathdoc.md` §3.2 与 §3.9、`~/imo-run/pbadvanced029/.mdc/files/`]：

| 现象 | 数据 | 所以 |
|---|---|---|
| LEAP（现成的 IMO 题 Lean 证明集）原样提交 | 基线 0 / 42 通过；改用 Lean 解析器后 17 / 42；被拒的 20 份在正文写了顶层 `open` / `variable` / `set_option` / `section` | 真实证明的常见写法，大半过不了形态规则 |
| Mathlib 文件整个转成节点 | 0 / 8,311 | 节点格式装不下一般的 Lean 文件 |
| LeanGround 的缺陷 | 9 个里有 8 个来自「用自己的近似去模拟 Lean 的解析和展开」 | 只要还在源码层近似 Lean，就会有下一个缺陷 |
| 第 1 轮（PB-Basic-018） | 1 个代理，不拆解，29 分钟写出 84 行，1 次提交通过 | 小题整份写完最快 |
| 第 2 轮（PB-Advanced-029），第一个项目 | 11 次根拆解全部被拒，约 2 小时 14 分钟；其中 3 个原因是 LeanGround 缺陷 | 时间耗在认证管线上，不在数学上 |
| 第 2 轮，重建后的项目 | 3 小时 40 分钟；13 个目标、12 个拆解、约 1,070 行；owner 审了 7 个拆解后放弃审阅 | 拆解能走通，但没有显示出提速；逐个审拆解跟不上 |

两轮的题目、代理和工具版本都不同，n = 2，所以以上只是观察，不是对照实验。

### 2.3 OpenAI 仓库体现的做法

本机副本：`.openai-math-corpus/upstream/`，`openai/math` 的 `1581d4cbd`。

**局限**：这是浅克隆，只有 1 个提交，也就是一次性发布的成品 [实测：`git rev-parse --is-shallow-repository`]。
另外，`reasoning_traces/` 不在本地检出里；有一篇论文的 `INPUTS.md` 提到作者与组件审阅记录在 coordination 目录，而这个目录没有公开。
所以下面关于「怎么做出来」的说法，都是从成品的形状推断的。

已知事实 [实测：README、`lean/formalization.yaml`、`ComparatorChallenges/*.json`]：

- 结果由一个未发布的内部模型产出。平均每个结果约 3 小时 ChatGPT Pro 思考算力，共提出约 4,000 个问题，筛选后成册；
  约 42% 的主要结果有 Lean 形式化。
- 每个结果走四步：论文（TeX）→ 陈述文件（定义自成一体，定理以 `sorry` 结尾）→ 证明工程（`OAI/<题目>/` 下若干文件）→ Comparator。

5 道题的证明工程 [实测：按 `import` 行求导入闭包，声明按第 0 列正则计数]：

| | Seymour | Hadwiger | Naimark | Kaplansky | DirectCrouzeix |
|---|---|---|---|---|---|
| 文件 | 43 | 288 | 16 | 121 | 42 |
| 行数 | 4,904 | 40,064 | 25,947 | 13,131 | 7,431 |
| 导入图深度 | 13 | 155 | 13 | 120 | 41 |
| 形状 | 有分叉的有向无环图 | 大体是链 | 接近链 | 纯线性链 | 41 个文件的链，`Main` 导入全部 |
| 定理与引理 | 261 | 1,787 | 1,544 | 708 | 340 |
| 定义类声明（`def`、`structure`、`instance` 等） | 84 | 1,280 | 554 | 409 | 78 |
| `set_option maxHeartbeats` | 0 | 225 | 0 | 0 | 0 |

五道题都是 0 个 `sorry`、0 个 `axiom`、0 个 `native_decide`。所以：

- **OpenAI 也在拆解，但拆在论文引理和文件这一层。** Seymour 的 `Main.lean` 只有 22 行，用 `counterexample_reduction`、
  `Pruning.pruning`、`Extremal.no_strictSubsetGrowth_of_pruning` 三条引理证出主定理。它们分别来自 Reduction、Pruning、
  ExtremalContradiction 三个文件，对应论文第 1–3 节；其余约 35 个文件是工程细节 [实测：导入关系与 `Main.lean`；与论文的对应是推断]。
- **线性链的工程更像先连续写完、再切块** [推断]：Kaplansky 和 DirectCrouzeix 每个文件只导入前一个，按 100–300 行切开。
- **中间没有认证。** 只有 Comparator 对最终定理的一次检查。
- **跨题复用很少**：413 个证明模块的导入闭包共 107,978 个文件，其中 92,726 个（86%）只被 1 道题用到，单个文件最多被 6 道题用到，
  也没有公共库目录 [实测]。所以跨题的细粒度复用，在这批数据里价值不大。
- **证明普遍使用 MathDoc 节点禁止的写法**：命名空间、`instance`、属性、`set_option`。所以按现在的格式，这些证明一份也交不进来。

### 2.4 两种做法各自的长处

| 需要 | 更合适的一方 | 理由 |
|---|---|---|
| 把万行级的证明做出来，并且可信 | OpenAI 的做法 | 用的是完整的 Lean；最后一次 Comparator 核验已经覆盖陈述、公理和内核 |
| 多个代理并行，进度看得见，半成品可以被放心引用 | MathDoc 的设计 | 没有中间认证，别人引用半成品时没有保证 |
| 同一项目里相同的命题只证一次 | MathDoc 的设计 | 按目标身份合并；OpenAI 没有对应机制 |
| 陈述忠实于数学 | 两边都靠人 | OpenAI 用范围说明标出排除的部分；MathDoc 由 owner 审根陈述 |

所以，本方案不照搬 OpenAI 的做法：只在最后核验一次，就失去了「半成品可被放心引用」，而这是多人协作的前提。
本方案要借来的是 OpenAI 做法里的「完整 Lean」和「最后一次可复核的整体核验」，并把 MathDoc 的认证单位放大到能装下它们。

## 3. 方案

### 3.1 总体

```
项目开头（模块）＋ 共享模块 D1, D2 …（按内容寻址）
目标 G（冻结类型 → GoalKey）
 ├─ 贡献 C1：模块 {C1/Reduce.lean, C1/Main.lean}；根定理连接到 G；占位 P、Q     ← 拆解
 │     P、Q 各自成为目标，陈述里的新定义在 D1
 └─ 贡献 C2：模块 {C2/Main.lean}；根定理连接到 G；无占位                       ← 完整证明
组装：选路线 → 取路线上各贡献的常量 → 改名、接线 → 从空环境整体重放 → 对根的冻结类型比对签名、收集公理
```

### 3.2 贡献：一组完整的 Lean 模块

- **写法**：任意 Lean 写法，包括命名空间、`instance`、属性、`set_option`、`private`、多文件，只受 §3.5 的常量层策略约束。
- **能导入什么**：基座（Mathlib）、项目开头模块、共享模块。不能导入别的贡献（§6 待定 2）。
- **根定理**：贡献要指明一条声明作为根。服务端用 `docs/13` 阶段 2a 的连接定理，把它连到目标的冻结类型，只允许宇宙参数实例化。
- **占位**：证明体恰好是 `sorry` 的定理，按 Lean 语法树判断（`docs/13` 阶段 1 已实现）。每个占位 resolve 成一个目标。
  所以代理的写法和现在一样：拆解就是写几条 `sorry` 引理，再用它们证出目标。
- **定义**：新目标的陈述用到的新定义，必须放在共享模块里，按内容寻址登记；证明这些新目标的人导入同一个共享模块。
  共享模块可以带引理：Seymour 的定义和基础引理混在 4 个文件里（§5.1），要求「只含定义」就得改上游源码。
  共享模块整体认证一次：每个常量只用允许的公理、没有占位、全部过内核。

### 3.3 认证一份贡献

1. **在沙箱里编译。** 把贡献的文件放进项目的 Lake 工作区（Mathlib + 项目开头 + 用到的共享模块），用 Lake 编译。
   编译期可以执行任意代码，例如 `#eval`、`run_tac`、宏 [实测：LeanGround `docs/13` §4.1，`run_tac` 能写文件]，所以必须在沙箱里编译。
2. **读出新常量。** 直接读贡献模块的 `.olean`，取出这些模块产生的全部常量，包括 Lean 自动生成的附属常量。
   不要导入贡献的模块：导入会把它依赖的 Mathlib 再载入一遍，原型里这一步占了单次认证的大部分时间和内存（§5.1）。
   基座（Mathlib、项目开头、共享模块）由常驻的检查进程导入一次。
3. **常量层检查：**
   - 根定理能连接到冻结目标；
   - 语法上恰好是 `sorry` 的定理记为占位，每个占位就是一个前提；
   - 从连接定理出发收集公理，遇到占位就停止。结果必须落在允许的集合里（`propext`、`Quot.sound`、`Classical.choice`；
     `native_decide` 按现有复核规则处理）。出现 `sorryAx` 或新的 `axiom` 声明，都拒绝；
   - 把贡献产生的全部常量在基座环境里重放。不是只重放「本次新增」的那一条声明。
4. **产出认证**：目标的 GoalKey、前提的 GoalKey 集合、贡献的内容哈希、可信等级。它和现在的认证含义相同，所以看板不用改。

和现在的区别：

- 不再有源码形态规则。
- 不再要求每个 `sorry` 引理都被直接用到：没用到的占位不会出现在公理收集里，自然也不算前提。
- 拒绝原因只能来自 Lean 的编译结果，或来自 §3.5 写明的常量层策略。这就是 LeanGround `docs/13` §3 的目标表述，只是范围从一条声明扩大到整组模块。

### 3.4 组装：常量层合并，从空环境重放

- **选路不变**（`docs/mathdoc.md` §4.9）。
- **合并**：取路线上每份贡献的常量，然后做三件事：
  - **改名**：每份贡献的常量加上自己的前缀，例如 `MDC.C<认证短号>.`。这样两份贡献各有一条 `helper` 时也不会冲突；
  - **接线**：每个占位常量的值，换成它的提供者的连接定理。类型不变，因为只有冻结类型相同的认证才会被选为提供者；
  - **共享**：共享模块和基座的常量按名字共享，内容必须一致。
- **重放与比对**：从空环境整体重放（和 Comparator 的第 3 步相同），再从根收集公理。
- **根陈述也是一份贡献**：冻结的根陈述单独成一个模块，它唯一的占位就是陈述本身，接到证明上。两者是否一致由内核判断，
  不比较类型的结构：IMO 029 的陈述含 `{(k : ℕ) | …}`，会生成名字随所在声明变化的 `match_1`，结构比较判为不等，内核连接通过（§5.1）。
- **为什么不在源码层组装，也不重新用 Lake 编译**：
  - 源码拼接是现在 9 个缺陷里 3 个的来源；
  - 重新编译时，A 贡献里的全局 `instance` 或 `simp` 属性会改变 B 贡献的展开方式，B 可能到组装时才失败；
  - 常量层合并只依赖内核，不受这两个问题影响 [推断，阶段 0 验证]。
- **可选的对外产物**：另外生成一个 Lake 项目，用 Comparator 跑一遍，交给第三方复核。这个项目如果因为上面第二个原因编译失败，不影响认证结论。

### 3.5 策略：从源码形态改到常量层

| 规则 | 现在（源码层） | 模块模式（常量层） |
|---|---|---|
| 允许的写法 | 声明白名单 | 任意 |
| `sorry` | 只能是整个引理体，且必须被直接用到 | 只能是占位定理的整个证明体；别处的 `sorry` 会让公理收集出现 `sorryAx`，于是被拒 |
| `axiom` 声明 | 禁止 | 禁止：公理收集里出现白名单以外的公理就拒绝 |
| 编译期执行代码 | 语法上拒绝 `#` 命令和 `run_tac` | 靠沙箱隔离；认证只看编译出的常量 |
| 名字 | 不得带撇号，不得 `private` 等 | 任意；组装时改名 |
| 规模 | 一条声明 | 多文件；单份贡献的上限待定（§6 待定 6） |

### 3.6 不变的部分

- 目标与目标身份：由冻结类型计算（`docs/13` 阶段 2a）；
- 且/或结构、路线、目标状态（`insufficient` / `derivable` / `certified`）；
- 可信等级、证否、尝试笔记、租约、`mdc next` 的调度信号；
- owner 在开局冻结根陈述。

### 3.7 MathDoc 侧

- **工作文件**：`mdc pull` 写出一个 Lake 工作区目录，里面有 lakefile、项目开头模块、共享模块、写着目标陈述的 `Goal.lean`，
  以及放贡献的 `Work/`。它取代单文件的 `mdc-goal-file/1`（`docs/mathdoc.md` §4.11）。
- **命令**：
  - `mdc check DIR`：交给 LeanGround 在沙箱里编译，返回诊断和 `sorry` 处的证明目标；
  - `mdc prove DIR` 和 `mdc split DIR`：走同一个提交接口，有没有占位决定它是完整证明还是拆解。
- **文档**：一份贡献写回成若干文件节点，Lean 块放模块原文，依赖边是 `import`。这和导入项目的文件节点是同一种节点
  （`docs/external-proofs.md` §3.3）。目标节点放冻结陈述。
- **审阅**：owner 只审根陈述，在开局时冻结。拆解默认直接生效，owner 可以事后停用（§6 待定 4）。
- **非形式证明**：目标可以挂在 LaTeX 或文字节点上；拆解的初稿来自论文或非形式证明的引理图。Seymour 的顶层结构就是这样（§2.3）。
- **与现有模式的关系**：新项目建立时选择「声明模式」或「模块模式」（§6 待定 1）。

### 3.8 导入项目接着协作

已导入的 OpenAI 结果，可以直接作为模块模式项目的起点：

- 该题的证明文件经过项目核验后，作为项目开头的一部分；
- 范围说明里排除的论断，成为新目标。

例如 Seymour 论文第 4–5 节的推论没有形式化（§2.3）。所以试点可以直接用真实的研究级任务，不必另外找题。

## 4. 代价与风险

### 5.2 阶段 1 的设计（2026-10-15）

在 LeanGround 里加一个验证组件 `lean-modules`，产出与现有认证同一种记录（`kind = certificate`），只是
`source_format = lean-modules-v1`。所以项目、可见范围、事件、推导查询（`query`）、组装计划（`plan`）都沿用现有实现；
MathDoc 在阶段 2 才接入。

| 部分 | 做法 |
|---|---|
| Lean 检查程序 | `Tools/ModuleCert.lean`（`lean_exe module_cert`），只依赖 Lean 核心库。从 stdin 读一个 JSON 请求：认证、共享模块、组装三种。内核重放用自带的一份 `replay`（照 Lean 核心库的 `Lean.Replay`，作用在 `Kernel.Environment` 上），所以同一份源码能在 4.33 与 4.34 上编译 |
| 目标身份 | `type_key` 与 `verify_worker` 用同一套算法（擦约束变量名、展开本次生成的辅助常量）；项目开头为空。陈述引用到的共享模块记进 GoalKey 的「定义」一项，与声明模式里「陈述直接引用的已登记定义」同一个位置；证明内部用到的共享模块不影响身份。所以只依赖基座的命题，两种模式得到同一个 GoalKey；一条路线上所有认证的环境也相同，可以直接用现有的组装计划。（初稿把共享模块记进项目开头：029 的根陈述不用定义、根认证要导入定义模块，两者环境对不上，所以改了。） |
| 陈述来源 | 每个模块模式的目标记下「陈述来源」：哪一份产物里的哪个常量。根目标来自登记的陈述模块；前提目标来自第一次提出它的拆解里的占位。认证时把来源里的陈述常量接到提交的根定理上，由内核判断（§3.4） |
| 产物 | 文件集合按内容寻址：`fact_artifact` 存规范 JSON（路径 → 原文），编译产物放 `<home>/modules/<sha>/<运行时>/` |
| 编译 | 按文件间的 `import` 排序，逐个 `lean -R src -o …olean`；LEAN_PATH = 基座 + 用到的共享模块 + 本产物。别的贡献不在路径上，所以「不能导入别的贡献」由构造保证。macOS 上包一层 `sandbox-exec`：只许写本产物的编译目录和临时目录，禁网络 |
| 接口 | `POST /v1/modules/shared`（登记共享模块）、`/v1/modules/resolve`（登记陈述，得 GoalKey）、`/v1/modules/check`（只编译与检查，不入库）、`/v1/modules/submit`（认证）；组装沿用 `POST /v1/facts/plan` 与 `/v1/facts/assemble`，计划里全是模块认证时走常量层组装 |
| 混用 | 一条路线里同时有声明模式和模块模式的认证时，组装明确拒绝（`mixed_source_formats`），阶段 1 不支持 |

**验收**：阶段 0 的三组经服务通过；`docs/13` 的对抗用例（名字遮蔽、错误目标、宇宙特例）在模块模式下同样成立；
沙箱里 `#eval` 写用户目录失败；两种模式对同一条只依赖 Mathlib 的命题给出同一个 GoalKey。

**实施中发现并改掉的两处**：

1. **共享模块不能进项目开头**。初稿把用到的共享模块记进 GoalKey 的项目开头：029 的根陈述不用定义、根认证要导入定义模块，

2. **Lean 只认 LEAN_PATH 上第一个含模块顶层目录的条目**。Seymour 的共享模块与提供者都在 `OAI/…` 下，分开给目录时提供者自己的

**验收脚本自己的一处错误**（不是服务的问题）：拆分带定义的陈述时，先把「定理之前的全部内容」都放进共享模块，3 题失败：
紧贴定理的文档注释落进共享模块末尾成了语法错误（Adv-014、Adv-030），`variable` 被移走后陈述里的变量失效（Basic-014）。
改为文档注释跟定理走、`open`/`variable`/`universe` 两边都留，3 题重跑通过。所以把陈述的定义拆进共享模块不是纯机械操作，
阶段 2 的 `mdc` 要给出这一步的工具或提示。

**比声明模式严的地方**：连接只许宇宙参数个数相同。宇宙多态的证明连不到 `Type` 版本的目标（声明模式可以，按宇宙实例化）。
不会误收，但会少收。

### 5.4 阶段 2 的设计（2026-10-15）

要回答的问题：一个项目怎样从建项起就用模块模式，`mdc` 的动词怎样处理整组文件，认证怎样写回文档；同时声明模式不受影响。

| 部分 | 做法 |
|---|---|
| 模式 | 放在证明环境里：`mode: "declarations" \| "modules"`，缺省是声明模式。模块模式的环境不许有 context 与 options（每个文件自带 `open`、`set_option`）。环境 ID 只在模块模式时把 `mode` 算进去，所以已有环境的 ID 不变；改模式就是改环境，旧看板照旧被取代。v1 合同（`proof-environment.v1`）是冻结的，不加字段 |
| 文档 | 模块模式下每个带 Lean 块的节点是一个完整的 Lean 文件，原文不改。模块名取 Lean 块元数据 `lean_module`、`import_module`（导入项目的文件节点），都没有时用节点自带的 `module`（例如 `Lib.N_<id>`）。根节点是陈述文件；从根出发沿依赖边或文件头的 `import` 能到的 Lean 节点，挂载时作为一个共享模块整体登记（`/v1/modules/shared`），再登记陈述（`/v1/modules/resolve`）。根文件里要恰好有一条 `sorry` 定理，或用元数据 `lean_conclusion` 指明 |
| 看板 | 看板记 `mode: "modules"` 与 `review: "none"`（§6 决定 4）。目标多记「陈述来源」：根目标是根节点的文件，前提是提出它的拆解认证加占位名。共享模块按 ID 记在 `shared_modules`。组装一律用 `lean-modules` 组件。声明模式专用的 `submit`、`resolve`、`submit_node`、`negate` 在模块项目里以 `not_in_module_mode` 拒绝 |
| 工作目录 | `mdc pull GOAL` 写一个目录：陈述来源的文件作为起稿（根目标复制到 `Work/Main.lean`；前提原样复制拆解的文件），陈述用到的共享模块按模块路径放好、设为只读，另有 `GOAL.md` 写明目标与规则。记录在 `.mdc/files/<目录>.json`，租约、重放、`done`、`note` 与单文件相同 |
| 提交 | `mdc check DIR` 走 `/v1/modules/check`；`mdc prove DIR`、`mdc split DIR -m` 发新命令 `submit_modules`，作业调 `/v1/modules/submit`。目录里除共享模块（改过就拒绝，`shared_module_modified`）之外的 `.lean` 文件都是贡献。根定理默认是陈述常量，`--root` 可改。`split --shared FILE` 把新定义所在的文件先登记成共享模块 |
| 写回 | 路线上每份认证的每个文件建一个节点（Lean 块是原文，元数据记模块路径与认证 ID）；边是认证内部的 `import`、对共享模块节点的 `import`、拆解到提供者。拆解登记的共享模块也建节点。根节点的文本不改（它是陈述），只记最终认证。写回建的文件节点标 `contribution`，以后挂载时不当作共享模块 |
| LeanGround | 三处小改：`resolve` 可省 `statement`，取唯一的占位；`submit` 接受 `mode`（`leaf` / `sketch`），入库之前核对；`submit` 的回复带上前提的完整身份（`premise_goals`），模块的 `read` 返回文件 |

**验收**：一个模块模式项目从建项走到写回；声明模式的项目行为不变，现有测试全过（§5 表）。

### 5.5 阶段 2 的结果（2026-10-15）

实现：MathDoc `coordinator/src/modules.ts`（项目文件、显示用的陈述、模块草稿、写回）、`src/mdc/module-dir.ts`（工作目录），
`proof.ts`（模式）、`domain.ts`（看板与 `submit_modules`）、`worker.ts`（挂载、提交、写回）、`http.ts`（草稿与检查）、
`mdc` 的 `pull/check/prove/split` 与 MCP 工具；网页的证明环境表单加了模式，模块认证按文件显示。LeanGround 的三处改动见 §5.4。

**测试** [实测]：

|---|---|---|
| MathDoc 新增 `coordinator/test/modules.test.ts` | 6 项 | 4 项纯逻辑；1 项用 LeanGround 的合同替身走完整流程；1 项接真实 LeanGround |

**验收：一个模块模式项目从建项到写回**（`modules.test.ts`，n = 1）。真实 LeanGround 是从 `project-checks` 工作树另起的一个实例
（端口 28765、单独的数据库、基座行复制自正式库，Lean 4.33.1 + Mathlib），正式服务 8765 没有动。[实测]

- 流程：共享模块节点（`def double`）与导入它的根陈述节点 → 建项（共享模块、陈述登记）→ `mdc pull` 得到目录 → `mdc check` →
  `mdc split`（一个占位，直接生效）→ 拉前提，目录里是拆解的原文 → `mdc prove` → 组装（`lean-modules`，从空环境重放）→ 写回
  → 再用一个新共享模块（`split --shared`）拆一次，新前提由真实内核接受。整段 6.2 秒。
- 拒绝：模块环境带 context、共享模块被改、`prove` 交了拆解（`has_premises`，入库之前）、根定理证的是别的命题、声明模式的 `submit`。
- 写回：两份认证各一个文件节点；根节点文本不变、记了最终认证，并依赖拆解的文件；拆解的文件依赖共享模块节点与前提的证明；分支没有因此过期。

**一条 Mathlib 命题走同一流程**（不入库的脚本，n = 2）[实测]：`2 * a * b ≤ a ^ 2 + b ^ 2`，`nlinarith` 证明。

| 步骤 | 第 1 次 | 第 2 次 | 所以 |
|---|---|---|---|
| 建项（登记陈述） | 89.0 秒 | 47.6 秒 | 慢在把 Mathlib 读进内存，见下一行 |
| 直接调 `/v1/modules/resolve` 两次 | 23.1 秒 | 4.3 秒 | 热的时候与阶段 0 的 2.5–7.8 秒同一量级 |
| `mdc check` | 46.7 秒 | 15.2 秒 | 同上 |
| `mdc prove --wait` | 2.4 秒 | 3.0 秒 | 编译结果已按内容缓存，只剩检查 |
| 组装 | 4.6 秒 | 8.2 秒 | — |
| 写回 | 0.06 秒 | 0.07 秒 | — |

当时交换区 12 GB 用了 11.2 GB，正式服务和 OpenAI 的 4.34.1 实例都在跑。所以前两步的长耗时，我认为来自内存紧张时 Mathlib 的
`.olean` 要重新换入，而不是模块模式本身 [推断：同一请求连跑两次从 23 秒降到 4 秒；没有在空闲机器上对照]。

**实施中发现的问题**：

1. **认证只记前提的 GoalKey，不记完整身份**。MathDoc 要为前提提交证明，需要完整的 GoalKey（`base_fingerprint`、
   `elaborated_proposition_hash` 等），而这些只能由 LeanGround 算出。声明模式靠从占位文本重新 `resolve` 得到；模块模式没有命题文本，
   所以改成由 `submit` 的回复带上 `premise_goals`。
2. **「证的是不是同一个命题」由内核按定义相等判断**。测试起初用拆解里的 `double_add`（`double n + 0 = n + n`）去证前提
   `double_eq`（`double n = n + n`），以为会被拒；真实内核接受了，因为 `n + 0` 按定义就是 `n`。这是正确的行为，
   阶段 1 也见过（§5.3）；替身按文本比较，判断不出来。所以反例改成了 `n = n`。
3. **写回的文件节点不能在下次挂载时被当成共享模块**。根节点写回后依赖证明文件；不加区分的话，再挂载一次时这些文件会沿依赖边
   被收进共享模块。写回的节点标 `contribution`，收集共享模块时跳过它们。
4. **协调服务的请求体上限是 2.2 MB**，比一份贡献能有的大小（LeanGround 收 32 MB 的请求体）小得多：Hadwiger 的证明有 40,064 行（§2.3），
   放不进去。命令接口与模块检查改为 32 MB，其余接口不变。

**未覆盖**：

- 证否（`mdc refute`）：模块目标没有命题文本，不能自动写出否定命题，阶段 2 直接拒绝。
- 已导入的项目接着协作（§3.8）：模块名已经认 `import_module`，但没有用导入项目实际走过。
- 显示用的陈述（看板上的 `declaration`）是从源码文本里找出来的，写法特别时可能缺失。它只用于显示，不参与认证。
- 第二个分支挂载、根或共享模块改过之后的过期提示，在模块模式下没有测试。
- `mdc check` 带新共享文件时，这些文件按贡献的一部分编译，用到它们的前提会报 `premise_uses_local_constant`；这一点没有测。
- 拉下来的目录不带 lakefile，不能在本机用 Lake 编译，只能用 `mdc check`。
- 网页上没有模块目标的专门视图；部署、Linux 沙箱、常驻检查进程仍是阶段 1 的未覆盖项。
