# 协作项目模型：Project、分解分支与 `mdc` 的角色

状态：**提议，待评审**（2026-09-30）。本文只是设计，没有改动代码。基线提交 `cc8ef1f`（分支
`codex/mathdoc-coordination`）；LeanGround 基线 `3965273`。

## 目的

本文回答两个问题：

1. 维护者提出的定义是：**Project 是一条定理的陈述、它的形式化证明，以及它的 Lean 证明图谱；不同分支对应不同的分解**。
   在多人加多个 Agent 的大规模协作下，这个定义的数据模型和交互应该怎么落地？
2. 用户既可以在浏览器侧栏的 Agent 聊天窗口里操作，也可以通过 Codex 等外部 Agent 调用 `mdc` 命令来分解证明。
   在这种模式下，`mdc` 应该承担什么，不应该承担什么？

## 背景

### 术语

| 术语 | 含义 |
|---|---|
| TerminusDB | 带分支和版本历史的图数据库。MathDoc 用它存文档节点，包括文字、LaTeX、Lean 块和依赖边 |
| LeanGround | 外部证明服务，负责检查 Lean 证明、保存认证，并把多条认证组装成完整证明 |
| 认证 | LeanGround 记下的一条事实：「在这些前提下，这条命题成立」。经过认可的验证组件检查后才会写入，写入后不改也不删 |
| 草图 | 带前提的认证。它的源码把子引理写成以 `sorry` 结尾的定理（`sorry` 是 Lean 里「此处先不证」的占位），再用这些子引理证出目标。草图由组件 `lean-worker-sketch` 检查 |
| 目标 | 一条待证的命题。它没有自己的名字，身份就是它的 GoalKey（见 §5.2） |
| GoalKey | LeanGround 对「某个环境下的一条命题」算出的规范化身份。同一条命题得到同一个 key，所以不同人拆出的同一条引理会自动合并 |
| AND-OR 图 | 证明图的形状。一个目标只要有一种拆法走通就算证出，这是「或」；一种拆法要求它的所有子目标都证出，这是「且」 |
| 看板 | 协调层在 PostgreSQL 里为一个证明请求保存的状态：目标、认证及其状态、任务、租约、预算、组装记录 |
| 租约 | 领取任务后获得的限时占用权，可以续期；带一个 epoch（代次编号），过期或被他人接手后，旧的持有人不能再结束任务 |
| 组装 | 从根出发选出一条路线，由 LeanGround 把路线上的各条认证拼成一份没有前提的文件，从头检查一遍 |
| 回写 | 把组装通过的源码写回 TerminusDB 的文档分支 |
| 幂等键 | 请求上附带的唯一 ID。服务端见到同一个键时返回第一次的结果，不会再执行一次 |

### 现状

- **文档层**：现在的一个 MathDoc 项目就是一个 TerminusDB 数据库，也称工作区；分支就是数据库分支。
  [实测：`docs/src/content/docs/concepts/workspaces.md`]
- **事实层**：LeanGround 只保存认证。它明确不保存目标列表、领取记录、失败尝试和拆法的启停状态。
  [实测：LeanGround `docs/11` §6.2]
- **协调层**：
  - 证明环境（基座、上下文、选项、最低信任等级）按分支存储，一个分支一份。[实测：`coordinator/src/proof.ts:65`]
  - 证明请求绑定在（数据库, 分支, 根节点）上，每个请求有一张看板，并在 LeanGround 注册一个独立的项目范围。
    [实测：`coordinator/src/domain.ts` 的 `documentCreateSchema`、`docs/src/content/docs/reference/proofs.md`「Running LeanGround」]
  - 认证进入看板后默认状态是 `active`。[实测：`coordinator/src/domain.ts:312`]
  - 只有从根出发、经 `active` 认证能到达的目标，才可以领取任务。[实测：`domain.ts:336-345`、`domain.ts:562`]
  - 一个项目的全部状态存成一条 JSONB 记录（PostgreSQL 的二进制 JSON 列），同一项目的写入靠行锁串行执行；
    没有做过大图和高并发的验收。[实测：`docs/src/content/docs/development/architecture.md:59`；`cc8ef1f:docs/coordination.md`「数据与身份」]
- **`mdc`**：HTTP API 的薄客户端，输出 JSON，不保存本地状态。和证明相关的只有
  `proof env/submit/list/status/command` 几条：
  - `proof command` 从标准输入读原始命令 JSON，每次调用都生成新的幂等键；
  - 没有 merge 命令。

  [实测：`coordinator/src/cli.ts:301-345`、`docs/src/content/docs/reference/workspace-commands.md`]
- **main 分支**的做法完全不同：
  - 每个节点编译成一个 Lean 模块，图的依赖边必须和 `import` 逐条一致，靠手工维护；
  - 本地 `lake serve` 为浏览器 Infoview（显示当前证明目标的面板）和 `mdc lean goals` 提供证明目标；
  - 节点显示绿、黄、灰三色状态。

  [实测：`git show main:docs/src/content/docs/reference/work-and-compilers.md`]

## 设计

### 1. 分支是共享证明图上的路线指针，而不是图的拷贝

「不同分支对应不同的分解」如果直接落在现状上，也就是一个分支一张看板、一个 LeanGround 项目范围，会出现三个问题。
下表说明每个问题的原因和后果：

| 问题 | 原因 | 后果 |
|---|---|---|
| 分支数爆炸 | 分解是递归的，每个子目标都可能有几种拆法。例如根有 2 种拆法，每种下面 3 个子目标各有 2 种，完整组合就是 2×2³ = 16 种 [推断：组合计数] | 分支只能表达顶层的选择，下层的替代拆法无处安放 |
| 进度不共享 | 每个证明请求在 LeanGround 注册独立的项目范围，认证只在范围内可见；导入别处的认证要求它已公开或共享到同一范围 [实测：`docs/src/content/docs/reference/proofs.md` 的 `import` 命令；`cc8ef1f:docs/coordination.md`] | 分支 A 证出引理 B 后，分支 B 里的 B 仍然是 `insufficient`，要么手动导入，要么公开。所以不同分支会重复劳动 |
| 冲突回来了 | 文档节点是可变文本，两个分支改同一条引理就得合并，而 `mdc` 没有合并命令 | 认证最大的优点被丢掉了：只追加、按 GoalKey 自动合并、不产生冲突 |

修正方式借用 git 的结构。git 的对象库按内容寻址、所有分支共享，分支本身只是一个指针。对应到这里：

- **LeanGround 的事实库相当于共享的对象库**：GoalKey 和认证 ID 都按内容寻址；
- **分支相当于指针**：它记录一条**路线**，即从根出发、在沿途目标上各选定一种拆法；再加上这条路线的非形式化蓝图，
  也就是 LaTeX 讲解文档。

这样「不同分支对应不同的分解」仍然成立：分支 X 在根上选拆法 D1，分支 Y 选 D2。但所有分支读写同一张图，
谁证出了 B，所有用到 B 的分支会同时更新。下图是一个例子：

```
Project（= 一个 TerminusDB 数据库）
│  根陈述 T（冻结）+ 证明环境（冻结）+ 成员
│
├─ 共享证明图（AND-OR 图，一张看板，一个 LeanGround 项目范围）
│     T ──┬── D1 ⇒ {A, B, C}
│         └── D2 ⇒ {B, E}          ← B 被两种拆法共用，只证一次
│                  C ──┬── D3 ⇒ {C1}
│                      └── D4 ⇒ {C2, B}
│
├─ 分支 main        路线 {T: D1, C: D3}   + main 上的蓝图节点
├─ 分支 strategy-2  路线 {T: D2}          + strategy-2 上的蓝图节点
│
└─ 形式化证明：某个分支的路线全部闭合 → LeanGround 组装出无前提的认证
```

子目标层的替代拆法（例如 C 的 D3 和 D4）不需要每一种都开分支，作为目标上的并列选项存在即可。
只有某个替代方案大到需要单独写蓝图、单独组织人力时，才值得开一个分支。

### 2. 数据模型

下表回答：每个概念放在哪里，能不能改。

| 概念 | 内容 | 存储 | 可变性 |
|---|---|---|---|
| Project | 根陈述、证明环境、成员。对应一个 TerminusDB 数据库，只有**一张看板、一个 LeanGround 项目范围** | PostgreSQL + LeanGround | 陈述和环境冻结；要改就开新的 Project |
| 目标 | 一条命题，按 GoalKey 去重 | LeanGround 登记 + 看板 | 身份不可变 |
| 拆法 | 一条草图认证，加上非形式化说明、状态和作者 | 认证在 LeanGround；其余在看板 | 认证不可变；状态可变 |
| 分支 | 路线：一张「目标 → 所选拆法」的表，允许部分目标未选；加上蓝图文档 | 路线在看板（待决定 C）；蓝图在 TerminusDB 分支 | 可变 |
| 文档节点 | 目标或定义的非形式化讲解，以及可选的 Lean 块，通过 GoalKey 绑定到共享目标 | TerminusDB 分支 | 可变 |
| 形式化证明 | 某个分支路线的组装结果 | LeanGround | 不可变 |

路线的语义：

- 已选的目标，组装时严格使用所选的拆法；
- 未选的目标，沿用现在的自动选路规则：在 `active` 的认证中优先选前提更少的。[实测：`proofs.md`「Assembly and writeback」]
- 所以一个新分支只需要在根上选一种拆法就能工作，下层按需再补选择。

文档节点与形式状态的关系：

- 节点显示的形式状态，一律按它绑定的 GoalKey 从共享看板读取，不再从本分支自己的证明请求推出。
  所以在分支 X 里证出的 B，在分支 Y 的 B 节点上同时显示为已证出。
- 两个方向的写入都保留：
  - 人在文档里写好 Lean 块，再提交节点，这是现在的 `submit_node`；
  - Agent 通过 `mdc` 直接提交证明或拆法，看板先更新；需要时再由回写在当前分支生成对应的文档节点。

下表列出与现状的差别，回答「要改哪里」：

| 项 | 现状 | 本设计 |
|---|---|---|
| 证明环境 | 一个分支一份（`mdc_environment` 按 `(database, branch)` 存） | 一个 Project 一份，所有分支共用 |
| 看板 | 一个证明请求一张，绑定（数据库, 分支, 根节点） | 一个 Project 一张 |
| LeanGround 项目范围 | 一个证明请求一个 | 一个 Project 一个 |
| 分支 | 独立的文档分支 | 路线加蓝图文档；形式状态来自共享看板 |
| 新拆法的默认状态 | `active` | `proposed`，可以按项目配置（待决定 B） |
| 可领取的目标 | 从根出发、经 `active` 认证能到达的目标 | 同上，另外按「被多少个分支的路线需要」排序 |

### 3. 拆法的生命周期与审阅

拆法是协作的基本单位，生命周期类似合并请求（Pull Request，PR）。下表回答每个状态的含义和由谁推进：

| 状态 | 含义 | 谁可以推进到这个状态 |
|---|---|---|
| `proposed` | 草图检查已通过，也就是「子目标全真 ⇒ 目标真」已经被机器确认；尚未审阅，不参与调度 | 提交者（任何成员或 Agent） |
| `active` | 审阅通过，参与调度和自动选路 | 维护者，或项目指定的审阅者 |
| `paused` | 暂停调度，比如怀疑某个子目标为假但还证不出否定；以后可以恢复 | 维护者 |
| `retired` | 有了更好的拆法，退役；事实仍然保留 | 维护者 |
| `refuted` | 某个子目标的否定已经被证出，这条拆法永远走不通 | 系统自动标记（依赖证否，见 §4 第 3 条） |

人的审阅只花在机器替代不了的地方。组装会把整条路线从头检查 [实测：LeanGround `docs/11` §8.4]，
所以「证明写得对不对」不需要人看。必须由人看的只有两件事：

1. **根陈述忠实性**：根陈述和它用到的定义，是否真的表达了想证的数学。这是整个 Project 唯一的信任根，开局就要冻结。
2. **拆法是否值得做**：草图检查只保证「子目标全真 ⇒ 目标真」，不保证子目标本身为真，也不保证子目标比原目标容易。
   拆法里新引入的定义，不需要做陈述忠实性审阅，因为最终组装出的结论是根陈述，与这些定义无关；
   但它们仍然属于「值得做」这项审阅的范围。[推断：依据 LeanGround `docs/11` §6.3、§8.4 的设计]

默认改为 `proposed` 的理由：Agent 多了以后，大量未经审阅的拆法会把调度摊薄到不值得做、甚至为假的子目标上 [推断]。
小项目可以通过项目配置恢复自动启用。

### 4. 大规模协作的交互原则

这一节回答：人和 Agent 多起来以后，流程上应当遵守什么。

1. **只追加的事实，尽量少的可变状态。** 证明和拆法都是只追加的认证，按 GoalKey 自动合并。需要协调的可变状态
   只剩四类：租约、拆法状态、分支路线、尝试笔记。所以冲突只会发生在这四类状态上。
2. **租约只用来减少重复劳动，不是独占权。** 租约过期后才交上来的正确证明照样接收，这一点现状已经如此
   [实测：`docs/src/content/docs/concepts/collaboration.md`]。难的目标应允许多人同时做。
3. **需要证否机制。** Agent 容易写出看似合理、实际少了一个前提条件的错误引理 [推断]。证出 ¬P 之后，
   所有包含 P 的拆法应自动标为 `refuted`，并停止调度。这一项现在明确没有实现
   [实测：`cc8ef1f:docs/coordination.md`「证否关联……不在本次实现中」]，而且还需要 LeanGround 侧的数据契约。
4. **共享失败记忆。** LeanGround 按设计不保存失败尝试，所以协调层要给每个目标挂上简短的尝试笔记：试了什么、
   卡在哪个证明目标。对一群 Agent 来说，这是省预算最直接的手段 [推断]。
5. **形式图由认证推导，不手工维护。** main 分支要求依赖边与 `import` 手工保持一致；本设计中「且」边直接来自
   草图的前提，自动得到。手工维护的依赖边只保留给非形式化的知识依赖。
6. **调度信号来自图。** 推荐下一个目标时，综合考虑三件事：它被多少个分支的路线需要、所在路线离闭合还差多少、
   已经失败过几次。

### 5. `mdc` 的角色

**`mdc` 是所有执行者共用的唯一「动作面」。** 执行者包括浏览器侧栏的 Agent、Codex、Claude Code、脚本，
以及在命令行里操作的人。它把协作协议的细节（修订号、幂等键、租约续期、GoalKey 解析）封装成数学工作流层面的动词，
地位类似 GitHub 协作里的 `gh` 加 `git`。

`mdc` 不承担以下四种职责：

- **裁判**：证明对错由 LeanGround 的验证组件裁决；
- **事实来源**：状态以服务端看板为准，`mdc` 的本地状态只是缓存和重放记录；
- **证明搜索**：搜索由 Agent 自己完成；
- **维护者决策**：启用拆法、组装、回写仍由维护者决定。`mdc` 提供这些命令，权限在服务端校验。

#### 5.1 现状差距

下表回答：现在的 `mdc` 离这个角色还差什么，每一项对 Agent 有什么影响。[实测：`coordinator/src/cli.ts`、
`docs/src/content/docs/reference/agents.md`]

| 现状 | 对 Agent 的影响 |
|---|---|
| `proof command` 读原始 JSON，调用方要自己知道命令格式、任务 ID 和租约 epoch | Agent 得先读完 150 行的 `agents.md` 才会用，容易拼错字段 |
| 每次调用都用 `crypto.randomUUID()` 生成新的幂等键 | 断网后重试会变成第二次提交。现有文档也写明：需要重放安全就别用 `mdc`，直接调 HTTP |
| 拆法提交后，新子目标只有 GoalKey，要有人把陈述手写一遍再 `resolve` | 提交的源码里本来就有每个 `sorry` 定理的陈述，所以这一步可以自动完成 |
| 没有续租辅助 | 长任务容易因为忘了 `heartbeat` 而丢掉租约 |
| 没有「只检查、不入库」的快速反馈 | Agent 的迭代循环只能走正式提交（原因见 5.4） |

#### 5.2 目标的引用与工作文件

本节回答：§5.3 动词里的 `GOAL` 指什么，以及目标需不需要一种专门的文件格式。

**目标本身不是文件，而是一条不可变的记录。** 它的全部内容是「陈述文本 + 陈述直接用到的定义 ID + Project 环境」，
由此算出 GoalKey。GoalKey 由六部分哈希而成 [实测：LeanGround `src/leanground/contracts.py:61-110`]：

- 基座指纹；
- 命题经过 elaboration（Lean 把源码解析、补全为内核表达式的过程）之后的哈希。约束变量名在这一步被擦除，
  所以变量改名不改变身份；
- 局部上下文，即 `open`、`set_option` 等行；
- universe 参数的个数；
- 相关的 Lean 选项；
- 命题直接引用的已登记定义 ID，没有引用时这一项不计入。

结果是一个 64 位十六进制的 SHA-256 值。陈述一改就成了另一个目标，所以目标创建之后没有可以编辑的内容，
它只存在于 LeanGround 的登记和看板里。

**目标没有自己的名字。** 名字来自提到它的定理声明，例如草图里的 `helper`。同一个目标在不同草图里可以叫不同的名字，
LeanGround 也允许多个声明绑定到同一个 GoalKey [实测：LeanGround `docs/12` 第 175 行]；反过来，不同草图里同名的定理
也可能是不同的目标。所以名字不能拿来当引用。

命令行参数的写法：

| 参数 | 接受的写法 |
|---|---|
| `GOAL` | 完整的 GoalKey；或它的唯一前缀，至少 8 位，有歧义时报错并列出候选（与 git 短哈希的做法相同）；或绑定到该目标的文档节点的标题或 UUID |
| `DEC` | 拆法所对应的草图认证 ID，或它的唯一前缀 |
| `RUN` | 组装记录的 ID |
| `FILE` | 一份工作文件，见下 |

看板和 `mdc goals` 的输出中，每个目标给出短前缀和一个展示名。展示名取第一次出现时的定理名，只用于阅读，不能当引用。

**工作文件是一份完整的 `.lean` 文件，细节规范见 `docs/coordination-goal-file.md`（`mdc-goal-file/1`）。** 要点如下：

- 文件由分隔行 `-- mdc: edit below this line` 分成两段：
  - 只读的前段：`import`、环境上下文、已登记定义的源码、尝试笔记快照，由 `mdc` 生成并用哈希保护；
  - 可编辑的正文：可用前提（证明为 `sorry` 的占位定理）、结论定理、辅助声明。
- 把结论的 `sorry` 换成完整证明，用 `mdc prove` 提交；新增若干以 `sorry` 为证明的定理，再用它们证出结论，用 `mdc split` 提交。
  新增的定理会成为新的子目标；如果某个新定理的 GoalKey 恰好等于已有目标，就自动与已有目标合并，Agent 不需要自己区分。
- 提交的源码只是正文。从文件到请求只有三步确定的变换：去掉前段、去掉未被引用的可用前提、规范化换行；`--dry-run` 打印实际要提交的源码。

正文对应现有草稿接口 `GET /api/projects/:id/nodes/:node/draft` 返回的 `source` 字段
[实测：`coordinator/src/http.ts:321-345`]。现状有三处不足：

- 草稿只对绑定了文档节点的定理生成。草图拆出、没有文档节点的子目标拿不到草稿，所以服务端要改为按目标生成，
  依据是看板里的陈述和定义 ID；
- 子目标在 `resolve` 之前只有 GoalKey、没有陈述，无法生成草稿。所以 §5.3 的自动 `resolve` 是 `pull` 的前提；
- 草稿以 JSON 返回，`mdc` 里没有对应的命令 [实测：`coordinator/src/cli.ts`]。

选用普通 `.lean` 文件的理由：

- Codex、Claude Code 这类 Agent 的基本操作本来就是读写文件、运行命令；
- 前段加正文是一份完整的 Lean 文件，LeanGround 兼容 `lean` 命令的垫片可以直接检查它 [实测：LeanGround `docs/10` §4.2]。
  但垫片按 `import` 自动挑选基座，不一定是 Project 固定的基座，所以这只是近似检查，以 `mdc check` 为准；
- 看到的与提交的只差上面三步确定的变换，所以 Agent 不会因为格式转换而提交出与所见不同的内容。

**元数据放在 `.mdc/` 里。** 文件对应的 Project、GoalKey、结论名（`expected_root`）、定义 ID、前段哈希、当前租约和提交记录，
记在工作目录的 `.mdc/` 中，按文件路径索引；`.mdc/` 不保存访问令牌。前段里的说明注释只供人阅读，`mdc` 判断文件对应哪个目标时不读它。
即使 Agent 改了目标定理的陈述，也不会记下错误的结果：LeanGround 会核对结论的实际类型与请求的 GoalKey 是否一致，
不一致时以 `proposition_differs` 拒绝 [实测：LeanGround `docs/12` 第 203 行]。

**文档里也不需要新的节点类型。** 一个目标在文档里可以有对应节点，也可以没有。有的话就是现有的定理节点：
Lean 块里恰好一个 `theorem`，证明为 `sorry` 时就是开放目标 [实测：`docs/src/content/docs/reference/proofs.md`「Node conversion」]。

#### 5.3 动词

下表回答：Agent 完成「找活 → 做 → 交」这个循环需要哪些命令。

| 动词 | 做什么 | 使用者 |
|---|---|---|
| `mdc goals [--open] [--branch B]` | 列出目标、状态，以及每个目标被多少个分支的路线需要 | 所有人 |
| `mdc next` | 按 §4 第 6 条的调度信号推荐一个目标并领取 | 成员 |
| `mdc show GOAL` | 查看陈述、已有拆法及其状态、尝试笔记、有哪些拆法等着它 | 所有人 |
| `mdc pull GOAL` | 写出工作文件：环境头、可用前提（`sorry` 占位）、目标陈述，附上尝试笔记 | 成员 |
| `mdc check FILE` | 只检查不入库：返回诊断，以及每个 `sorry` 处的证明目标（见 5.4） | 成员 |
| `mdc prove GOAL FILE [--wait]` | 提交完整证明，可选等待判定结果 | 成员 |
| `mdc split GOAL FILE -m 说明 [--wait]` | 提交拆法；检查通过后自动为每个新子目标 `resolve` 陈述，返回新子目标列表 | 成员 |
| `mdc note GOAL 文本` | 写尝试笔记 | 成员 |
| `mdc done [--spent N] [--outcome O]` | 结束租约并报告实际花费；领取期间后台自动续租 | 租约持有人 |
| `mdc branch new NAME --pick T=D2`、`mdc route [BRANCH]` | 开一条策略分支；查看路线和闭合进度 | 编辑者及以上 |
| `mdc review DEC --activate/--pause/--retire` | 审阅拆法 | 维护者 |
| `mdc assemble [--branch B]`、`mdc accept RUN` | 组装、回写 | 维护者 |

自动 `resolve` 放在服务端的提交作业里完成，不放在 `mdc` 里，这样浏览器和侧栏 Agent 也能受益。
从源码提取陈述是纯语法转换，例如把 `theorem h (n : Nat) : n + 0 = n` 转成 `∀ (n : Nat), n + 0 = n`。
转换错了也是安全的：服务端要求解析出的 GoalKey 与已知的 key 一致，否则作业以 `identity_mismatch` 失败，
不会记下错误的陈述。[实测：`agents.md`「New subgoals」]

#### 5.4 `mdc check` 的前提

LeanGround 已有的 `/v1/check` 满足不了 `mdc check` 的需要。[实测：LeanGround `src/leanground/server.py:136`、
`src/leanground/check.py` 的 `CheckResult`]

- 它按文件里的 `import` 在 Init、Lean、Mathlib 中自动挑选基座，而不是使用 Project 固定的 `base_key` 和上下文；
- 它不认识项目里登记过的定义；
- 它返回诊断、公理和信任等级，不返回 `sorry` 处的证明目标。

可行的做法有两种，列为待决定 E：

1. LeanGround 新增一个按项目环境检查草稿的接口：输入基座、上下文、定义 ID，只检查不写入，并返回每个 `sorry` 处的证明目标；
2. `mdc` 或服务端自己拼出完整文件，再改写每个 `sorry`：tactic 模式下改写为 `trace_state; sorry`，term 模式下改写为
   `(by trace_state; sorry)`，让证明目标以 info 诊断的形式返回。这两种改写能否在所有位置取得正确的证明目标，
   需要实测 [未验证]。

LeanGround 文档报告 `/v1/check` 单次耗时 0.05–0.18 秒（这是 LeanGround 自己的实测，本仓库未复测）。
所以无论选哪种做法，只要复用它的常驻 worker，就足以充当 Agent 每一步的反馈。

#### 5.5 工程性质

1. **输出**：默认 JSON；错误带稳定的错误码和下一步提示，例如 `stale_lease` 提示「重新 `mdc claim`」。
   人类可读的输出用 `--text` 开启。
2. **本地状态只用于重放**：`.mdc/` 目录保存幂等键、原请求和当前租约。重试同一个意图不会重复提交，续租在后台自动完成。
   删掉 `.mdc/` 只会丢失重放能力，不会丢失服务端数据。
3. **身份**：每个 Agent 进程使用自己的委托子令牌，例如 `alice/codex-1`。权限可以收窄到只能 claim / submit / note，
   不能 activate / accept；审计和预算按 Agent 记账。现在的 `MDC_ACTORS` 是一张静态令牌表 [实测：`docs/src/content/docs/reference/configuration.md:20`]，
   所以需要先增加委托子令牌。
4. **一份实现，两个入口**：`mdc mcp` 把同一组动词暴露为 MCP 工具（Model Context Protocol，一种让聊天式 Agent
   调用外部工具的标准协议），供侧栏 Agent 使用；Codex 和 Claude Code 直接调用命令行，再配一份 `AGENTS.md` 说明工作循环。
   两边行为一致，区别只在于由谁来触发操作。

### 6. 侧栏聊天 Agent

侧栏 Agent 和 Codex 的区别只在入口：

- **身份**：登录用户的委托子令牌。
- **上下文**：当前选中的目标或节点，以及当前分支。
- **工具**：只有 §5.3 的动词，不拥有直接写数据库的特权。它提交的拆法和 Codex 提交的走同一条路：
  草图检查 → `proposed` → 审阅。
- **运行位置**：服务端，通过 LeanGround 做检查，所以用户本机不需要安装 Lean。这和阶段 3 把本地 Lean 移出默认构建的方向一致。
- **界面**：对话中显示它执行的每条 `mdc` 命令，并链接到对应目标。维护者级的操作（启用拆法、组装、回写）只生成
  待确认的按钮，由人来点。

### 7. 从 main 分支借鉴什么

| 借鉴 | 不借鉴 |
|---|---|
| 每个 `sorry` 处的证明目标反馈（原 `mdc lean goals`），放进 `mdc check` | 依赖边与 `import` 手工保持一致的约束 |
| 节点三色状态，扩展为 certified / derivable / insufficient / proposed / refuted | 每节点一个 Lean 模块、依赖本地 Lake 构建 |
| Infoview 这种给人用的交互式证明面板，作为可选扩展保留 | 本地 Lean 服务进程 |

### 8. 落地阶段

每个阶段列出要做的事和验收标准：

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1. 共享看板 | 证明环境和看板从按分支改为按 Project；分支改为路线；节点形式状态按 GoalKey 读共享看板 | 两个分支选不同的根拆法、共用引理 B：在一个分支证出 B 后，另一分支的 B 节点同时显示已证出，并且不需要任何导入 |
| 2. `mdc` 动词层 | 先做 `pull / check / split / prove / done`；本地 `.mdc/` 重放；自动续租；服务端自动 `resolve` | 断网重试不重复提交；一个 Agent 只用这五个动词，就能把一个目标拆开并证完 |
| 3. 审阅 | `proposed` 状态、审阅视图、尝试笔记 | `proposed` 的拆法不产生可领取的任务；启用后才产生 |
| 4. Agent 入口 | 委托子令牌、`mdc mcp`、侧栏 Agent | 侧栏 Agent 与命令行 Agent 执行同一流程，审计记录显示的执行者是子令牌 |
| 5. 规模与证否 | 看板拆表；证否；`mdc next` 调度 | 负载测量：参与者数量、目标数量和写入延迟的目标在本阶段开始前定下 |

阶段 1 会把所有分支的写入集中到同一行 JSONB 上，写入热点因此比现在更集中。阶段 1 先不拆表，但必须在阶段 5 之前做负载测量，
再决定何时拆表（见「未覆盖」）。

## 结论

1. **Project 的构成**：根陈述、冻结的证明环境、一张共享的 AND-OR 证明图，加上组装出的形式化证明。一个 Project
   对应一个 TerminusDB 数据库，只有一张看板和一个 LeanGround 项目范围。
2. **分支确实对应分解，但分支只是共享图上的路线指针加蓝图文档，而不是整张图的拷贝。** 否则分支之间无法共享已证出的引理
   （现在是一个证明请求对应一个 LeanGround 项目范围），分解的递归还会让分支数爆炸。
3. **人只审两件事**：根陈述是否忠实、拆法是否值得做。其余交给草图检查和组装。拆法像合并请求一样，从 `proposed`
   走到 `active`；另外还需要补上证否机制和尝试笔记。
4. **`mdc` 是所有 Agent 和人共用的动作面。** 它提供数学层面的动词，保证重放安全、自动续租，并提供只检查不入库的快速反馈；
   侧栏 Agent 和 Codex 通过命令行和 MCP 两个入口使用同一组动词。它不做裁判、不保存事实、不搜索证明，也不替维护者做决策。

## 未覆盖

- 没有运行系统，也没有做任何规模实验，本文所有规模判断都是 `[推断]`。
- **共享看板的写入热点**：现在一个项目的状态存成一条 JSONB 记录，靠行锁串行写入，并且没有做过大图和高并发验收
  [实测：`cc8ef1f:docs/coordination.md`]。所有分支共用一张看板后，写入竞争会集中到这一行。所以要支撑大规模协作，
  目标、任务、尝试需要拆成独立的表，具体时机取决于阶段 5 的负载测量。
- 证否在 LeanGround 侧的数据契约没有设计，包括 ¬P 怎样与 P 的 GoalKey 关联。
- 分支级权限没有设计：谁能修改哪条路线、谁能审阅哪条拆法。
- 侧栏 Agent 在服务端运行时的沙箱和费用控制没有设计。
- 文档节点通过 GoalKey 绑定共享目标之后，现有「过期」判定怎样改没有细化。现在的判定依据是根节点、直接前提和所用定义的
  Lean 文本指纹，按证明请求记录。
- `trace_state` 改写方案（§5.4 做法 2）能否在 tactic 模式和 term 模式的所有 `sorry` 位置取得正确的证明目标，没有实测。
